Apa Ini Sebenarnya?

Metode strategi menguji program secara bertingkat: dari jutaan tes fungsi kecil (Unit Test) yang murah dan kilat, hingga tes simulasi menyeluruh (E2E Test).

Masalah Nyata Apa yang Diselesaikan?

Menguji seluruh aplikasi secara manual dengan tangan memakan waktu berhari-hari dan sering kecolongan bug kritis saat software dikirim ke pelanggan.

Analogi Kehidupan Sehari-Hari

Ibarat uji kelayakan mobil: baut dan rem diuji satu per satu di lab (Unit Test), mesin dipasang ke rangka (Integration Test), baru mobil diajak jalan di sirkuit (E2E Test).

Kapan Kita Memakainya?

Wajib diterapkan sebelum melakukan peluncuran aplikasi ke dunia nyata agar Anda tidur nyenyak di akhir pekan tanpa teror telepon server eror.

Modul 26: Piramida Testing, TDD & Contract Testing

Membangun rasa percaya diri tanpa batas saat melakukan rilis kode: dekonstruksi proporsi Piramida Testing (Unit vs Integrasi vs E2E), disiplin Test-Driven Development (TDD), pengujian kontrak API terdistribusi antar microservices dengan Pact, dan automasi browser headless via Playwright.

1. Proporsi Ideal Piramida Testing (Mike Cohn Model)

Sistem pengujian software modern tidak menguji segalanya lewat browser pengguna. Kita membagi pengujian menjadi lapisan berjenjang:

Puncak (10%)
End-to-End (E2E) Tests
Menguji alur kritis pengguna dari browser riil via Playwright (misal: checkout bayar). Lambat (hitungan menit) & mahal biaya komputasi.
Tengah (20%)
Integration & Contract Tests
Menguji interaksi antar komponen nyata (Repository SQL riil di Testcontainers, Contract API Pact). Selesai dalam hitungan detik.
Fondasi (70%)
Unit Tests
Menguji logika bisnis murni fungsi/metode secara terisolasi dengan mock. Super kilat (ribuan test dalam 200 milidetik)!

2. Bahaya Anti-Pattern "Ice Cream Cone"

Banyak tim engineering terjebak membuat piramida terbalik (*Inverted Testing Pyramid*):

Kerugian Ice Cream Cone Testing
Ketika sebuah tim memiliki 500 test E2E UI dan hanya 20 unit test:

1. Pipeline CI Lambat: Menjalankan build memakan waktu 45 menit, melumpuhkan produktivitas developer.
2. Flaky Tests: Uji browser sering gagal mendadak akibat animasi CSS atau gangguan jaringan sesaat (*false positive*).
3. Sulit Root Cause: Saat test E2E gagal, developer tidak tahu apakah bug ada di frontend, gateway, database, atau token auth!

3. Disiplin Test-Driven Development (TDD)

TDD bukan tentang menguji kode; TDD adalah alat perancangan arsitektur perangkat lunak melalui siklus tiga langkah:

1. FASE MERAH (RED)
Tulis 1 test unit kecil untuk perilaku yang diinginkan. Jalankan test → Test WAJIB GAGAL (karena implementasi kodenya belum ada sama sekali).
2. FASE HIJAU (GREEN)
Tulis kode implementasi paling minimal dan sederhana hanya agar test tersebut lulus menjadi hijau. Jangan over-engineering!
3. REFACTOR
Bersihkan struktur kode, hilangkan duplikasi, optimalkan efisiensi tanpa mengubah perilaku. Seluruh unit test tetap hijau!

4. Consumer-Driven Contract Testing (Pact) di Microservices

Di arsitektur microservices, tim Frontend (Consumer) sering kali rusak ketika tim Backend (Provider) mendadak mengubah nama kolom JSON API tanpa pemberitahuan.

Bagaimana Pact Bekerja?

  • Consumer (Frontend) menulis spesifikasi harapan payload ke dalam berkas kontrak JSON Pact.
  • Kontrak diunggah ke Pact Broker.
  • Di pipeline CI backend, provider memverifikasi kodenya terhadap kontrak tersebut sebelum diizinkan merge. Jika backend melanggar kontrak, CI backend seketika gagal diblokir!

5. End-to-End Modern dengan Playwright

tests/checkout.spec.ts (Playwright)
import { test, expect } from '@playwright/test';

test('Alur transaksi checkout keranjang belanja berhasil', async ({ page }) => {
  await page.goto('https://shop.velora.id/cart');
  
  // Auto-waiting locator bawaan Playwright mengeliminasi flaky tests!
  await page.getByRole('button', { name: 'Checkout Sekarang' }).click();
  
  await page.getByPlaceholder('Alamat Pengiriman').fill('Jl. Sudirman No 45, Jakarta');
  await page.getByRole('button', { name: 'Konfirmasi Bayar' }).click();
  
  await expect(page.getByText('Pesanan Berhasil Dibuat!')).toBeVisible();
});

6. Production War Stories & Anti-Patterns

War Story: Perubahan Field API 'user_id' Menjadi 'userId' Melumpuhkan Aplikasi Mobile
Tim backend sebuah aplikasi transportasi online merapikan kode mereka ke gaya camelCase, mengganti respons JSON user_id menjadi userId.

Semua unit test backend lulus 100%. Namun begitu dirilis ke staging/produksi, jutaan aplikasi mobile iOS & Android crash total saat login karena parser JSON mobile mengharapkan user_id snake_case!

Solusi: Menerapkan Pact Contract Testing di CI/CD. Perubahan nama field pada schema API seketika terdeteksi melanggar kontrak Consumer Mobile dan langsung membatalkan deployment sebelum sempat menyentuh server staging!

7. Kuis Uji Pemahaman: Piramida Testing & TDD

1. Mengapa anti-pattern 'Ice Cream Cone Testing' (proporsi E2E jauh lebih banyak daripada Unit Test) sangat dihindari dalam software engineering modern?
A. Karena E2E test dilarang oleh standar industri
B. E2E test sangat lambat dieksekusi, membutuhkan biaya komputasi tinggi, dan sering menimbulkan kegagalan semu (flaky tests) yang sulit dilacak akar masalahnya
C. Karena unit test membutuhkan waktu berjam-jam untuk dijalankan
2. Apa fungsi utama dari Consumer-Driven Contract Testing menggunakan kakas seperti Pact dalam arsitektur microservices?
A. Merancang antarmuka frontend secara otomatis
B. Memastikan bahwa perubahan skema API pada service backend tidak merusak ekspektasi payload data yang dibutuhkan oleh aplikasi consumer (frontend/client)
C. Menghitung kapasitas beban server CPU
