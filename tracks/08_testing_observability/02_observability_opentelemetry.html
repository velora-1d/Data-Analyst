Fase 27: Tiga Pilar Observability & OpenTelemetry

Melihat tembus pandang ke dalam labirin sistem terdistribusi: dekonstruksi Tiga Pilar (Structured Logs, Metrik RED/USE Prometheus, dan Distributed Traces OpenTelemetry), transmisi konteks lintas microservice dengan standar W3C Trace Context (traceparent), serta optimalisasi Tail-based Sampling.

1. Tiga Pilar Observability: Bukan Sekadar "Pasang Log"

Ketika aplikasi mengalami error di produksi, insinyur membutuhkan 3 sumber informasi yang saling berkorelasi:

Pilar Format Data Teknologi Standar Pertanyaan yang Dijawab
1. Metrics Angka agregat time-series numerik (Counter, Gauge, Histogram) Prometheus, Grafana, Mimir "Apakah ada masalah sekarang?" (Contoh: Error rate naik 5% atau CPU 95%).
2. Traces Rentang waktu bersarang (*Spans*) dari request awal hingga selesai OpenTelemetry, Jaeger, Grafana Tempo "Di microservice mana dan query apa waktu terbuang?" (Menemukan bottleneck latensi).
3. Logs Pesan teks terstruktur JSON dengan timestamp dan konteks Grafana Loki, OpenSearch "Apa pesan error dan stack trace penyebab spesifiknya?"

2. Metrik Standar Industri: RED vs USE

Metrik RED (Untuk Layanan API / Web)
• R (Rate): Jumlah request per detik (Requests/sec).
• E (Errors): Jumlah kegagalan HTTP 5xx per detik.
• D (Duration): Latensi durasi request (P50, P95, P99).
Metrik USE (Untuk Hardware & OS)
• U (Utilization): Persentase waktu perangkat sibuk (CPU 80%).
• S (Saturation): Antrean pekerjaan yang tertunda (Load Average).
• E (Errors): Kesalahan perangkat keras (Network packet drops).

3. Distributed Tracing: Anatomi Trace & Spans

Ketika 1 klik checkout dari pengguna memicu 10 panggilan RPC lintas service (Frontend → Gateway → Order Service → Payment → Inventory → PostgreSQL), OpenTelemetry mengikat seluruhnya ke dalam satu Trace ID yang sama.

Setiap operasi individu disebut sebagai Span (memiliki nama, start time, end time, dan tag atribut seperti http.status_code=200 atau db.statement="SELECT...").

4. Bedah Header Standar W3C `traceparent` (RFC)

Bagaimana Trace ID bisa berpindah lintas bahasa (Node.js → Go → Java)? Melalui HTTP header standar global W3C Trace Context:

Format HTTP Header
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
              │                 │                                │         │
              │                 │                                │         └─ 4. Flags (01 = Recorded/Sampled)
              │                 │                                └─ 3. Parent Span ID (8-byte hex)
              │                 └─ 2. Global Trace ID (16-byte hex)
              └─ 1. W3C Version (00)

Setiap kali sebuah service memanggil service lain, ia menyematkan header traceparent ini, sehingga mesin visualisasi seperti Jaeger dapat merajut seluruh span menjadi satu diagram waterfall yang runtut!

5. Strategi Sampling: Menghemat Biaya Cloud Telemetri

  • Head-Based Sampling: Keputusan merekam diambil di pintu masuk awal (misal secara acak merekam 1% dari total trafik). Cepat dan hemat CPU, namun berisiko melewatkan 99% error yang langka!
  • Tail-Based Sampling: Seluruh span disimpan di buffer memori OpenTelemetry Collector hingga request selesai. Jika request mengalami error HTTP 500 atau latensi > 1 detik → Direkam 100%! Jika request sukses normal → dibuang untuk menghemat ruang penyimpanan.

6. Production War Stories & Anti-Patterns

War Story: Latensi Misterius 4 Detik Terpecahkan dalam 2 Menit dengan Distributed Trace
Sebuah layanan e-commerce mengalami lonjakan latensi halaman keranjang belanja menjadi 4 detik setiap kali pengguna memiliki lebih dari 15 barang.

Tim engineering menghabiskan waktu berhari-hari membaca log teks berantakan tanpa hasil karena semua status mengembalikan HTTP 200 OK.

Solusi: Begitu OpenTelemetry Distributed Tracing diaktifkan, grafik waterfall Jaeger langsung memperlihatkan kenyataan visual yang mencolok:
Sebuah span fungsi checkDiscount() melakukan 15 kali pemanggilan query SQL serial secara berulang-ulang di dalam loop (N+1 query problem)! Developer memperbaiki kode menjadi 1 query SQL WHERE item_id IN (...) dalam 10 menit, memangkas latensi dari 4.000ms menjadi 35ms!
