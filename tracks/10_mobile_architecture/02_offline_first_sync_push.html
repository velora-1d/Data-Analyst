Modul 32: Arsitektur Mobile Offline-First, Local Database & Push Notifications

Membangun aplikasi mobile kelas dunia yang tangguh di segala kondisi jaringan internet: arsitektur *Local-First* berbasis SQLite, sinkronisasi dua arah dengan resolusi konflik data (CRDTs vs LWW), manajemen background worker ramah baterai (Android WorkManager & iOS BackgroundTasks), serta bedah protokol transmisi *Push Notifications* waktu-nyata (Apple APNs & Google FCM).

1. Realitas Jaringan Mobile: Jaringan Selalu Fluktuatif (*Flaky Network*)

Berbeda dengan komputer server di data center yang terhubung kabel serat optik gigabit tanpa putus, smartphone hidup di dunia yang sangat tidak menentu:

  • Pengguna masuk ke dalam lift beton atau terowongan kereta (kehilangan sinyal seketika).
  • Perpindahan antena seluler (*tower handoff*) dari 5G ke 3G yang memicu lonjakan latensi dari 20ms ke 3.000ms.
  • Pengguna menyalakan Mode Pesawat (*Airplane Mode*).
Prinsip Dasar Offline-First
Aplikasi mobile yang baik tidak boleh menampilkan layar pemuatan (*loading spinner*) berputar-putar tanpa henti hanya karena koneksi internet mati. Aplikasi wajib langsung terbuka dan menampilkan data terakhir yang tersimpan di perangkat dalam waktu 0 milidetik.

2. Local Database sebagai Single Source of Truth (SSOT)

Dalam arsitektur *Offline-First*, antarmuka (UI) tidak pernah membaca data langsung dari network API. UI hanya boleh mengamati (*observe*) **Database Lokal**:

Langkah 1: User Action
Optimistic UI Update
Pengguna mengklik tombol "Like" atau mengirim pesan chat. Pesan langsung muncul di layar dengan tanda centang abu-abu (0ms delay).
Langkah 2: Local Write
Tulis ke SQLite Lokal
Data disimpan ke database lokal (SQLite/Room/CoreData) dengan status sync_status = 'PENDING' dan dicatat ke antrean mutasi (Outbox Queue).
Langkah 3: Background Sync
Sinkronisasi ke Server API
Saat koneksi internet tersedia, background worker mengirim mutasi ke backend. Begitu server membalas 200 OK, status diubah menjadi 'SYNCED'.

3. Sinkronisasi Data & Resolusi Konflik: LWW vs CRDTs

Ketika pengguna mengedit data secara offline di dua HP berbeda pada saat yang sama, timbul konflik data saat kedua HP online kembali. Bagaimana menyelesaikannya?

1. Last-Write-Wins (LWW)
• Mekanisme: Mutasi yang memiliki timestamp paling akhir menimpa mutasi sebelumnya.
• Kelemahan Fatal: *Clock Skew* (jam pada HP pengguna bisa diatur manual oleh user atau berbeda beberapa detik antar pabrikan ponsel), menyebabkan data baru justru tertimpa data lama!
• Pencegahan: Menggunakan Logical Lamport Timestamps atau Server-side Timestamping.
2. Conflict-free Replicated Data Types (CRDTs)
• Mekanisme: Struktur data matematis yang menjamin bahwa jika beberapa replika menerima perubahan dalam urutan acak, status akhirnya akan selalu identik (konvergen) tanpa membutuhkan server penengah.
• Penerapan: Google Docs mobile, Notion offline editor, dan aplikasi kolaborasi teks modern.

4. Background Execution & Anggaran Baterai Ponsel

Sistem operasi modern (iOS & Android) menerapkan aturan agresif untuk menghemat baterai. Aplikasi yang berjalan di background akan dibekukan (*suspended*) atau dimatikan oleh sistem.

  • Android WorkManager: Framework resmi untuk tugas tertunda yang terjamin dieksekusi. Mendukung *Constraints*: setRequiredNetworkType(NetworkType.UNMETERED) (hanya jalan saat Wi-Fi) dan setRequiresCharging(true) (hanya saat dicas).
  • Android Doze Mode: Saat layar HP mati dan tidak bergerak di atas meja, OS menunda semua akses network hingga jendela pemeliharaan (*maintenance window*) berikutnya.
  • iOS BackgroundTasks Framework: Menggunakan BGAppRefreshTask (refresh konten pendek) dan BGProcessingTask (tugas berat seperti sinkronisasi database offline saat HP dicas di malam hari).

5. Arsitektur Push Notifications: Apple APNs & Google FCM

Bagaimana aplikasi seperti WhatsApp atau Gojek dapat menampilkan notifikasi pesanan secara instan meskipun aplikasinya sedang dimatikan total (*swiped away*) oleh pengguna?

Koneksi Tunggal Berdaya Rendah (The Single Persistent TCP TLS Connection)
Smartphone tidak membuka koneksi terpisah untuk tiap aplikasi (karena akan menguras baterai dalam 2 jam). Sebaliknya, sistem operasi menjaga 1 buah koneksi TCP socket TLS tunggal berdaya sangat rendah ke server Apple (APNs) atau Google (FCM).
Tahap 1: Registrasi
Pendaftaran Device Token
Aplikasi meminta token perangkat ke OS. OS menghubungi APNs/FCM dan mengembalikan 64-karakter Device Token unik ke backend server Anda.
Tahap 2: Pengiriman
Backend → APNs/FCM via HTTP/2
Backend Anda memanggil API APNs/FCM via protokol HTTP/2 dengan autentikasi JWT token (p8 key untuk Apple).
Tahap 3: Delivery
OS Menampilkan Notifikasi
APNs/FCM mendorong payload JSON ke HP via koneksi socket yang sudah standby. OS memproses payload dan menampilkan banner notifikasi di layar kunci.

6. Production War Story: Badai 100K Mutasi Pesawat (*Airplane Retry Storm*)

Bencana Kasus Nyata: Server Backend Ambruk Pasca Musim Mudik Lebaran

Sebuah aplikasi e-commerce tiket dan perhotelan memiliki fitur ulasan hotel offline. Ribuan pengguna yang berada di pesawat menulis ulasan dan mengunggah foto hotel secara offline sepanjang penerbangan 2 jam.

Dampak yang Terjadi: Saat pesawat mendarat di bandara dan ratusan penumpang mematikan Mode Pesawat secara bersamaan, aplikasi mendeteksi sinyal internet dan seketika mengeksekusi antrean mutasi lokal tanpa *jitter*. Lebih dari 100.000 aplikasi serentak meluncurkan request mutasi HTTP POST ke backend di detik yang sama. Server database origin kolaps, CPU load melonjak ke 98%, dan API gateway menolak koneksi dengan error 504 Gateway Timeout.

Solusi Arsitektur: Tim merekayasa ulang modul sinkronisasi mobile dengan menerapkan:
1. Exponential Backoff with Full Jitter: Penjadwalan retry acak rand(0, min(cap, base * 2^attempt)) sehingga pengiriman mutasi terdistribusi merata dalam rentang 3-15 menit.
2. Batch Mutation API: Menggabungkan 50 mutasi lokal menjadi 1 payload biner tunggal (gRPC/Protobuf), menghemat 90% round-trip HTTP overhead!

7. Kuis Uji Pemahaman Mobile Data & Networking

1. Mengapa pada arsitektur mobile modern smartphone tidak mengizinkan setiap aplikasi membuka koneksi polling background sendiri-sendiri untuk menerima notifikasi?
A. Karena sistem operasi melarang aplikasi mengakses internet di background
B. Karena membuka puluhan koneksi socket terpisah akan menguras baterai ponsel secara drastis; OS menggantinya dengan 1 koneksi socket terpusat berdaya rendah via APNs/FCM
C. Karena protokol HTTP tidak mendukung format pesan push
2. Apa risiko utama dari strategi resolusi konflik data Last-Write-Wins (LWW) di aplikasi mobile offline?
A. Adanya fenomena Clock Skew pada jam ponsel pengguna yang dapat menyebabkan data terbaru justru tertimpa secara keliru oleh data lama
B. Database SQLite tidak mampu menyimpan data timestamp
C. LWW membutuhkan ukuran memori RAM yang terlalu besar
