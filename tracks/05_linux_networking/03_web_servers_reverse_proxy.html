Modul 19: Server Web, Reverse Proxy & Load Balancer

Arsitektur gerbang depan lalu lintas internet: perbedaan mendasar Forward vs Reverse Proxy, mikro-arsitektur Master-Worker Nginx berbasis Event Loop, komparasi perutean beban Layer 4 TCP vs Layer 7 HTTP, terminasi sertifikat SSL/TLS, serta konfigurasi upstream keepalive berkecepatan tinggi.

1. Forward Proxy vs Reverse Proxy

Banyak insinyur pemula sering tertukar antara dua fungsi proxy ini:

Forward Proxy (Melindungi Klien)
• Berada di depan sekelompok klien/pengguna.
• Bertindak atas nama Klien untuk menyembunyikan alamat IP asli pengguna dari website luar yang dikunjungi (contoh: VPN korporat, Tor).
• Server web tujuan mengira koneksi datang dari IP Forward Proxy.
Reverse Proxy (Melindungi Server)
• Berada di depan sekelompok server backend aplikasi.
• Bertindak atas nama Server: menyembunyikan IP privat server aplikasi, membagi beban trafik (Load Balancing), melakukan terminasi SSL, dan caching data statis (contoh: Nginx, Cloudflare, HAProxy).

2. Arsitektur Master-Worker Nginx: Mengapa Sangat Ringan?

Berbeda dengan server Apache lama yang membuat thread/proses baru untuk setiap 1 request pengguna (membuat server kehabisan RAM saat ada ribuan pengunjung), Nginx dirancang menggunakan arsitektur event-driven asinkron:

Proses 1
Master Process
Berjalan dengan hak istimewa root. Membaca konfigurasi berkas, mengikat port 80/443, dan memantau kesehatan proses worker.
Proses 2, 3, 4..
Worker Processes
Berjalan tanpa hak istimewa (user nginx), biasanya 1 worker per 1 core CPU fisik.
Mesin Event
epoll Event Loop
Tiap worker menjalankan non-blocking event loop yang sanggup menangani 10.000+ socket koneksi serentak pada 1 thread CPU!

3. Load Balancing: Layer 4 (Transport) vs Layer 7 (Application)

Parameter Layer 4 Load Balancer (L4) Layer 7 Load Balancer (L7)
Dasar Keputusan Routing Alamat IP dan Nomor Port TCP/UDP saja Header HTTP, Cookie, URI Path, Body JSON
Inspeksi Paket Tidak membaca isi pesan (Hanya merutekan paket biner mentah) Membaca isi pesan HTTP penuh (Terminasi TLS, inspeksi payload)
Kecepatan & Throughput Super Kilat (Jutaan paket per detik) Lebih lambat karena ada CPU overhead parsing HTTP/TLS
Fleksibilitas Routing Kaku (Semua trafik port 443 ke upstream yang sama) Sangat Cerdas: Rute /api ke Node.js, rute /gambar ke S3, rute /video ke CDN

4. Algoritma Distribusi Trafik

  • Round Robin: Membagikan request secara bergantian berurutan ke server 1, 2, 3, 1, 2, 3. Asumsi: seluruh server memiliki spesifikasi perangkat keras yang identik.
  • Least Connections: Mengarahkan request berikutnya ke server yang saat itu memiliki jumlah koneksi aktif paling sedikit. Sangat ideal untuk request yang durasi pengerjaannya bervariasi (misal upload file).
  • IP Hash: Menghitung hash dari IP klien untuk menentukan server target. Menjamin pengguna yang sama selalu tersambung ke server yang sama (Sticky Session).

5. Terminasi SSL/TLS & Upstream Keepalive

Konfigurasi Nginx Berperforma Tinggi
upstream backend_cluster {
    server 10.0.1.10:3000;
    server 10.0.1.11:3000;
    # Wajib aktifkan connection pooling upstream!
    keepalive 64;
}

server {
    listen 443 ssl http2;
    server_name api.velora.id;

    # Terminasi SSL dilakukan di Nginx (Bebaskan CPU Node.js dari enkripsi!)
    ssl_certificate /etc/ssl/certs/velora.crt;
    ssl_certificate_key /etc/ssl/private/velora.key;

    location / {
        proxy_pass http://backend_cluster;
        
        # Wajib set HTTP/1.1 dan kosongkan header Connection agar keepalive berfungsi!
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

6. Production War Stories & Anti-Patterns

War Story: Node.js Hang Akibat Menangani SSL Handshake Mandiri
Sebuah startup fintech mengarahkan trafik HTTPS publik langsung ke aplikasi Node.js mereka tanpa reverse proxy di depannya.

Ketika kampanye iklan viral diluncurkan, server menerima 5.000 handshake TLS serentak per detik.

Dampak: Operasi matematika kriptografi asymmetric handshake (RSA/ECDSA) memakan 100% CPU main thread Node.js, membekukan event loop dan menyebabkan response time API melonjak dari 40ms menjadi 12 detik!

Solusi: Memasang Nginx sebagai SSL Termination Reverse Proxy di depan Node.js. Nginx mengeksekusi handshake TLS menggunakan multi-worker C library yang sangat teroptimasi hardware, dan meneruskan trafik HTTP plain-text murni ke Node.js di jaringan lokal privat, menurunkan utilisasi CPU backend hingga 75%!

7. Kuis Uji Pemahaman: Server Web & Reverse Proxy

1. Apa perbedaan arsitektural mendasar antara Load Balancer Layer 4 (L4) dan Layer 7 (L7)?
A. L4 jauh lebih lambat daripada L7
B. L4 merutekan paket murni berdasarkan informasi IP dan port TCP/UDP, sedangkan L7 memeriksa isi aplikasi HTTP seperti URL path, headers, dan cookies
C. L7 hanya dapat digunakan untuk protokol email
2. Dalam konfigurasi reverse proxy Nginx upstream, mengapa kita harus menyetel 'proxy_http_version 1.1' dan mengosongkan header 'Connection'?
A. Agar server langsung memutuskan koneksi seketika
B. Mengaktifkan penggunaan kembali koneksi TCP (Connection Pooling / Keepalive) ke server backend aplikasi sehingga tidak perlu membuka-tutup socket per request
C. Menghapus enkripsi SSL secara permanen
