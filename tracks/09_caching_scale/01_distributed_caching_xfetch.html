Modul 29: Distributed Caching, Redis & Algoritma XFetch

Menghancurkan bottleneck database relational: arsitektur topologi caching (Cache-Aside vs Write-Through), mikro-struktur data Redis (SDS, SkipList, Single-Thread Event Loop), mitigasi fenomena mematikan Thundering Herd (Cache Stampede), serta implementasi algoritma probabilistik optimal XFetch.

1. Tiga Topologi Caching Terdistribusi

Pola Caching Alur Baca / Tulis Kelebihan & Resiko
Cache-Aside (Standar Industri) Aplikasi mengecek Redis dulu. Jika Miss, baca DB lalu simpan ke Redis dengan TTL. Paling tangguh: Jika Redis mati, aplikasi tetap hidup langsung membaca DB. Resiko: data bisa stale sesaat jika DB di-update tanpa memvalidasi cache.
Write-Through Aplikasi menulis ke Cache; Cache bertanggung jawab menulis ke Database secara atomik. Konsistensi data terjamin tinggi, namun operasi penulisan memiliki latensi dobel.
Write-Back (Write-Behind) Aplikasi menulis HANYA ke Cache; Cache menulis ke DB secara asinkron setiap 5 detik. Kecepatan tulis super kilat, namun berisiko kehilangan data jika mesin cache crash sebelum data terdorong ke harddisk DB.

2. Mengapa Redis Begitu Cepat? (100.000+ Operasi/Detik)

Banyak orang bingung mengapa Redis yang Single-Threaded bisa jauh lebih cepat daripada database multi-threaded:

RAM Murni
In-Memory Storage
Seluruh data disimpan langsung di RAM, mengeliminasi jeda I/O pencarian piringan disk secara permanen.
Tanpa Lock
Zero Lock Contention
Karena single-threaded, Redis tidak membuang siklus CPU untuk mutex locking atau thread context switching!
Struktur Canggih
SDS & SkipList
Menggunakan Simple Dynamic String (SDS O(1) panjang) dan SkipList hierarkis untuk operasi Sorted Set (ZSET) berkecapatan O(log N).

3. Bahaya Mematikan Cache Stampede (Thundering Herd)

Bayangkan sebuah kunci cache berita viral atau promo kilat diakses 20.000 kali per detik dengan TTL 10 menit.

Anatomi Bencana Cache Stampede
Tepat pada menit ke 10:00.001, kunci cache tersebut KADALUARSA (EXPIRED):

1. Dalam 10 milidetik berikutnya, 20.000 request pengguna membaca Redis dan semuanya mendapatkan Cache Miss!
2. Seluruh 20.000 proses serentak melakukan query kalkulasi SQL berat yang sama persis ke database utama PostgreSQL!
3. Connection pool database habis seketika, CPU database 100%, server database crash, dan seluruh aplikasi tumbang total!

4. Matematika Algoritma Probabilistik XFetch

Pada makalah ilmiah ACM "Optimal Probabilistic Cache Stampede Prevention" (Vattani et al.), para peneliti membuktikan bahwa kita tidak membutuhkan distributed lock yang lambat. Cukup gunakan rumus probabilitas eksponensial:

Rumus XFetch
Sebuah request memutuskan untuk menghitung ulang cache di latar belakang jika memenuhi syarat:

currentTime - (delta * beta * ln(random())) >= expirationTime

• delta: Durasi waktu yang dibutuhkan database untuk menghitung nilai ini (misal 50ms).
• beta: Parameter agresivitas (standar 1.0).
• random(): Angka acak murni antara 0 dan 1.
• ln(random()): Logaritma natural yang menghasilkan angka negatif acak.

Hasil Brilian: Saat cache masih baru, probabilitas refresh adalah 0%. Ketika mendekati detik-detik kadaluarsa, probabilitas meningkat secara eksponensial, sehingga TEPAT SATU request yang beruntung akan memperbarui cache sebelum kunci benar-benar mati, sementara 19.999 request lainnya tetap membaca cache lama dengan mulus!

5. Implementasi XFetch Produksi

utils/xfetchCache.ts
interface CacheEntry<T> {
    value: T;
    delta: number;      // Waktu komputasi dalam milidetik
    expiresAt: number;  // Timestamp kadaluarsa mutlak
}

async function getWithXFetch<T>(
    key: string,
    ttlMs: number,
    computeFn: () => Promise<T>,
    beta: number = 1.0
): Promise<T> {
    const cached = await redis.get<CacheEntry<T>>(key);
    const now = Date.now();

    // Logika Probabilistik XFetch:
    const shouldRecompute = !cached || 
        (now - (cached.delta * beta * Math.log(Math.random())) >= cached.expiresAt);

    if (shouldRecompute) {
        const start = Date.now();
        const freshValue = await computeFn();
        const delta = Date.now() - start;

        const newEntry: CacheEntry<T> = {
            value: freshValue,
            delta,
            expiresAt: Date.now() + ttlMs
        };

        // Simpan asinkron ke Redis
        await redis.set(key, newEntry, 'PX', ttlMs + 60000); // Ekstra buffer TTL
        return freshValue;
    }

    return cached.value;
}

6. Production War Stories & Anti-Patterns

War Story: Lonjakan Flash Sale 12.12 Merobohkan DB Akibat TTL Seragam
Sebuah platform e-commerce menyetel TTL 1.000.000 produk flash sale tepat 600 detik (10 menit).

Ketika flash sale dimulai pukul 00:00, seluruh produk dibaca dan disimpan ke Redis.

Dampak: Tepat pada pukul 00:10.00, seluruh 1.000.000 kunci cache KADALUARSA BERSAMAAN DALAM 1 DETIK YANG SAMA!

Terjadilah Massive Cache Stampede yang mengirim jutaan query SQL ke database, melumpuhkan seluruh transaksi belanja selama 45 menit!

Solusi Baku:
1. Terapkan Cache Jitter: Setel TTL dinamis: TTL = base_ttl + random(-60, 60).
2. Gunakan Algoritma Probabilistik XFetch untuk seluruh query halaman produk utama!
