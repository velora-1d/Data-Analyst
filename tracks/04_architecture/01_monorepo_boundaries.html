Ibarat Lemari Perkakas Terpadu Satu Bengkel
Apa Ini Sebenarnya?

Monorepo adalah strategi menyimpan seluruh kode proyek (web, HP, backend, desain) di dalam satu rumah besar dengan sekat kamar yang rapi.

Masalah Nyata Apa yang Diselesaikan?

Mencegah kode tercecer di puluhan tempat terpisah yang sering menyebabkan komponen web dan backend beda versi dan gagal jalan saat dirilis bersama.

Analogi Kehidupan Sehari-Hari

Ibarat perkakas satu bengkel di lemari raksasa: mekanik motor dan mekanik mobil berbagi kunci pas yang sama, sehingga tidak perlu membeli alat ganda berulang kali.

Kapan Kita Memakainya?

Ideal untuk tim berkembang yang mengelola beberapa aplikasi sekaligus yang saling berbagi komponen UI dan model data yang sama.

Modul 13: Monorepo vs Polyrepo & Module Boundaries

Membangun fondasi rekayasa perangkat lunak skala enterprise: strategi pemilihan Monorepo vs Polyrepo, akselerasi CI/CD berbasis Task Pipeline Caching (Turborepo/Nx), serta penegakan batasan modul domain melalui Hexagonal Architecture (Ports and Adapters).

1. Dilema Struktur Repositori & Spaghetti Dependencies

Ketika tim rekayasa berkembang dari 3 insinyur menjadi 50 insinyur dengan belasan microservice, tantangan terbesar bukan lagi menulis baris kode baru, melainkan mengelola batas dependensi (Module Boundaries) dan alur CI/CD.

2. Monorepo vs Polyrepo: Analisis Trade-off

Dimensi Evaluasi Polyrepo (Multi-Repo Terpisah) Monorepo (Satu Repositori Bersama)
Atomic Refactoring Sangat sulit. Mengubah skema DTO butuh PR di 5 repo berbeda dengan koordinasi versi rumit. Sangat Mudah. Mengubah kontrak API dan seluruh client frontend di 1 PR atomik tunggal!
Code Sharing Harus mempublikasikan package ke Private npm/NuGet registry per perubahan kecil. Langsung import modul via workspace: import { User } from '@repo/types'.
CI/CD Build Time Cepat di awal (hanya build 1 repo kecil). Bisa sangat lambat jika naif, namun super kilat jika menggunakan Smart Build Caching.
Akses Kontrol & Skala Isolasi permission ketat per repositori. Membutuhkan tooling canggih (CODEOWNERS, Turborepo, Nx, Bazel). Digunakan Google, Meta, Uber.

3. Task Graph & Remote Caching: "Never Build the Same Code Twice"

Kunci keberhasilan Monorepo modern (seperti Turborepo dan Nx) adalah Content-Aware Hash Caching:

Bagaimana Turborepo Menghitung Cache Hash?
Sebelum menjalankan build paket apps/web, Turborepo menghitung hash dari:
Hash = SHA256(Isi File Sumber + package.json + Dependensi Lokal + Variabel Env)

Jika hash tersebut sudah pernah di-build sebelumnya (oleh rekan tim Anda atau di CI server):
Turborepo me-replay artefak dist/ dan log terminal dalam waktu 150 milidetik (FULL TURBO)! CI pipeline yang tadinya memakan waktu 25 menit terpangkas menjadi 45 detik.

4. Clean Architecture & The Dependency Rule

Uncle Bob (Robert C. Martin) merumuskan aturan fundamental:
"Source code dependencies must point only inward, toward higher-level policies."

Lingkaran 1 (Inti)
Domain Entities
Objek bisnis murni. Nol dependensi ke database, framework, atau web HTTP!
Lingkaran 2
Use Cases
Alur proses bisnis aplikasi (misal: BayarPesananUseCase).
Lingkaran 3
Interface Adapters
Controller REST, Serializer JSON, Presenter UI, Repository Impl.
Lingkaran 4 (Luar)
Frameworks & Drivers
Express, Postgres, Redis, AWS S3. Komponen ini dapat diganti kapan saja tanpa menyentuh Domain!

5. Bedah Kode: Hexagonal Architecture (Ports and Adapters)

Bagaimana mengimplementasikan Dependency Inversion Principle (DIP) di TypeScript/Node.js?

1. Inward Port (Interface di Level Domain)
// domain/ports/PesananRepository.ts
// Domain TIDAK TAHU apakah data disimpan di Postgres, SQLite, atau Array Memori!
export interface PesananRepository {
    simpan(pesanan: Pesanan): Promise;
    cariBerdasarkanId(id: string): Promise;
}
2. Use Case (Hanya Bergantung pada Interface Port)
// application/use-cases/BuatPesanan.ts
export class BuatPesananUseCase {
    constructor(private readonly repo: PesananRepository) {}

    async execute(data: BuatPesananDTO): Promise {
        const pesanan = new Pesanan(data.id, data.total);
        pesanan.validasiBatasKredit(); // Logika bisnis murni!
        await this.repo.simpan(pesanan);
    }
}
3. Outward Adapter (Implementasi di Level Luar)
// infrastructure/adapters/PostgresPesananRepository.ts
export class PostgresPesananRepository implements PesananRepository {
    constructor(private readonly pgPool: any) {}

    async simpan(pesanan: Pesanan): Promise {
        await this.pgPool.query('INSERT INTO pesanan (id, total) VALUES ($1, $2)', [pesanan.id, pesanan.total]);
    }
}

6. Production War Stories & Anti-Patterns

War Story: ORM Leak Merusak Seluruh Arsitektur Microservice
Sebuah tim backend meneruskan objek entitas ORM Prisma/TypeORM langsung dari database hingga ke controller API dan view template.

Ketika perusahaan memutuskan untuk bermigrasi dari PostgreSQL ke DynamoDB untuk mendukung trafik jutaan pengguna, mereka menyadari bahwa seluruh logika bisnis di 40 controller terikat erat dengan dekorator dan metode spesifik SQL ORM tersebut!

Tim terpaksa melakukan penulisan ulang (rewrite) total selama 4 bulan penuh. Jika sejak awal mereka menerapkan batas Ports and Adapters, migrasi driver database hanyalah urusan menulis 1 kelas Adapter baru tanpa mengubah 1 baris pun kode bisnis Use Case!

A. Dari Domain Inti mengarah keluar menuju Database dan Framework
B. Dari layer luar (Database, Framework, UI) mengarah ke dalam menuju aturan Domain Bisnis murni

2. Bagaimana build system Monorepo cerdas (seperti Turborepo) dapat memangkas waktu eksekusi CI dari puluhan menit menjadi hitungan detik?
A. Dengan menghapus seluruh pengujian unit test secara otomatis
B. Menggunakan Content-Aware Hash Caching untuk merekam hash file sumber; jika paket belum berubah, ia me-replay artefak build dari remote cache secara instan
C. Memaksa seluruh kode dikonversi menjadi bahasa Assembly
