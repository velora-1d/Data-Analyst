Fase 15: Clean Architecture, Hexagonal & Onion Architecture

Membangun perangkat lunak yang kebal terhadap perubahan teknologi: prinsip pembalikan ketergantungan (Dependency Inversion), 4 lapisan konsentris Clean Architecture, arsitektur Hexagonal (Driving & Driven Ports), serta pengujian unit use case bisnis tanpa database.

1. The Dependency Rule: Arah Panah Ketergantungan

Dalam arsitektur tradisional berlapis tiga (Controller → Service → Database DAO), logika bisnis sering kali terikat kuat pada skema tabel SQL.

Hukum Utama Clean Architecture
"Source code dependencies must point only inward, toward higher-level policies."

Artinya: 1. Lapisan dalam (Domain & Use Case) SAMA SEKALI TIDAK BOLEH MENGENAL lapisan luar (Express, Postgres, AWS, Redis).
2. Perubahan pada framework web (misal Express ke Fastify) atau driver database (Postgres ke MongoDB) TIDAK AKAN MENGUBAH 1 KARAKTER PUN DI DALAM ATURAN BISNIS ANDA!

2. Empat Lapisan Konsentris Clean Architecture

Lingkaran 1 (Terdalam)
Domain Entities
Model bisnis inti & Value Objects murni tanpa import pustaka pihak ketiga mana pun.
Lingkaran 2
Use Cases
Orkestrasi alur data bisnis spesifik (misal: TransferSaldoUseCase, BatalkanPesanan).
Lingkaran 3
Interface Adapters
Penerjemah data: Controller HTTP REST, Presenter JSON, Repository SQL implementation.
Lingkaran 4 (Terluar)
Frameworks & Drivers
Detail teknis periferal: Database engine, Web server, Queue worker, UI template.

3. Hexagonal Architecture: Ports and Adapters

Alistair Cockburn memvisualisasikan aplikasi sebagai segi enam (Hexagon) yang berkomunikasi dengan dunia luar melalui Ports (Colokan/Interface) dan Adapters (Konverter Steker):

Port (Interface di Level Domain)
Kontrak abstrak yang mendefinisikan apa yang dibutuhkan oleh aplikasi:
interface PembayaranGateway { bayar(jumlah: number): Promise<boolean>; }
Adapter (Implementasi Spesifik)
Modul konkret yang menghubungkan port dengan teknologi vendor luar:
class MidtransPaymentAdapter implements PembayaranGateway { ... }
class StripePaymentAdapter implements PembayaranGateway { ... }

4. Driving (Primary) vs Driven (Secondary) Ports

  • Driving Ports (Inbound): Port yang menggerakkan aplikasi dari luar. Contoh: Controller HTTP menerima request pengguna dan memanggil Use Case.
  • Driven Ports (Outbound): Port yang digerakkan oleh aplikasi ke luar. Contoh: Use Case memanggil Port Repository database atau Port pengirim SMS.

5. Unit Testing Sub-Milidetik Tanpa Database

Karena Use Case hanya bergantung pada interface abstrak (Port), Anda dapat menguji seluruh skenario bisnis dalam waktu 2 milidetik menggunakan InMemory Repository Mock:

Unit Test Use Case (Nol Jaringan, Nol Database!)
// test/BuatPesanan.test.ts
class InMemoryPesananRepo implements PesananRepository {
    public data: Pesanan[] = [];
    async simpan(p: Pesanan) { this.data.push(p); }
}

test('Harus menolak pesanan jika total melebihi limit kredit', async () => {
    const mockRepo = new InMemoryPesananRepo();
    const useCase = new BuatPesananUseCase(mockRepo);

    // Jalankan tanpa koneksi Postgres nyata!
    await expect(useCase.execute({ id: 'P01', total: 99999999 }))
        .rejects.toThrow('Limit kredit terlampaui');
});

6. Production War Stories & Anti-Patterns

War Story: Pergantian Payment Gateway 1 Malam Berkat Hexagonal Ports
Sebuah startup travel mengalami insiden ketika penyedia Payment Gateway utama mereka mendadak mengalami gangguan sistem server fatal selama 24 jam penuh di musim liburan lebaran.

Berkat arsitektur Hexagonal Ports & Adapters, tim backend tidak perlu menyentuh satu baris pun kode logika pesanan atau perhitungan diskon kupon.

Mereka hanya menulis 1 file class adapter baru: BackupGatewayAdapter.ts yang mengimplementasikan interface PaymentPort yang sama, dan mengubah 1 baris di Dependency Injection container. Dalam waktu 2 jam, transaksi pembayaran kembali normal menggunakan gateway cadangan!

A. Menghilangkan kewajiban menjalankan CI/CD pipeline

C. Menghindari pembuatan file unit test
