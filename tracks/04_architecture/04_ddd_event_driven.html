Modul 16: Domain-Driven Design (DDD) & Event-Driven Architecture

Menyelaraskan kompleksitas model bisnis dengan kode perangkat lunak: Strategic DDD (Ubiquitous Language, Bounded Contexts), Tactical DDD (Entities, Value Objects, Aggregate Roots), serta eliminasi bahaya The Dual-Write Problem melalui Transactional Outbox Pattern.

1. Filosofi Domain-Driven Design (Eric Evans)

Banyak sistem software gagal bukan karena bug sintaks teknis, melainkan karena kesalahpahaman antara insinyur perangkat lunak dengan pakar domain bisnis (Business Stakeholders).
DDD mengajarkan bahwa perangkat lunak harus memodelkan realitas bisnis secara akurat dan menggunakan Ubiquitous Language: bahasa terpadu yang dipahami sama persis oleh Product Manager, Insinyur, dan Database Administrator.

2. Strategic DDD: Ubiquitous Language & Bounded Contexts

Salah satu kesalahan terbesar perancang sistem adalah memaksakan satu model data global universal (misalnya tabel User dengan 80 kolom).

Makna Bounded Context
Kata yang sama memiliki makna dan kebutuhan atribut yang sama sekali berbeda di konteks yang berbeda:
  • Konteks Autentikasi: User peduli pada email, password_hash, dan 2FA salt.
  • Konteks Pengiriman (Logistics): Customer peduli pada koordinat GPS alamat rumah dan nomor WhatsApp kurir.
  • Konteks Akuntansi (Billing): Client peduli pada NPWP, nomor rekening bank, dan batas kredit faktur.
Di DDD, ketiganya adalah model terpisah di dalam Bounded Context masing-masing!

3. Tactical DDD: Entity, Value Object & Aggregate Root

Konsep 1
Entity
Memiliki ID unik permanen sepanjang waktu. Contoh: Pesanan #104 (statusnya bisa berubah, tapi ID-nya tetap sama).
Konsep 2
Value Object
Immutable tanpa ID. Kesamaan dinilai dari nilai atributnya. Contoh: Uang { nilai: 50000, mataUang: 'IDR' }.
Konsep 3
Aggregate Root
Pintu gerbang konsistensi transaksional. Elemen luar hanya boleh memodifikasi anak entitas melalui gerbang Root!

4. Bahaya Maut: The Dual-Write Problem

Dalam arsitektur Event-Driven terdistribusi, pengembang sering kali menulis kode seperti ini:

Kode Berbahaya: The Dual-Write Bug
// 1. Simpan ke database SQL
await db.query('UPDATE pesanan SET status = "PAID" WHERE id = ?', [id]);

// 2. Publikasikan event ke Kafka / RabbitMQ
// BAHAYA: Jika server mati atau jaringan Kafka putus di baris ini...
await kafka.produce('order-events', { id, event: 'OrderPaid' });
// HASIL: Database sudah PAID, tapi modul Notifikasi dan Gudang TIDAK PERNAH TAHU!

5. Solusi Industri: The Transactional Outbox Pattern

Bagaimana menjamin pesan Kafka 100% pasti terkirim jika data SQL berhasil disimpan?

Mekanika Transactional Outbox
1. Buat satu tabel khusus di database SQL: outbox_events (id, agregat_tipe, payload_json, status, created_at).
2. Simpan mutasi data pesanan dan baris event outbox DALAM SATU TRANSAKSI ACID SQL TUNGGAL:
BEGIN TRANSACTION;
UPDATE pesanan SET status = 'PAID' WHERE id = 'ORD-101';
INSERT INTO outbox_events (payload) VALUES ('{"event":"OrderPaid","id":"ORD-101"}');
COMMIT;
3. Background worker (atau Change Data Capture / Debezium) membaca tabel outbox dan mem-forward event ke Kafka.
4. Jaminan Mutlak: Jika transaksi SQL rollback, event tidak akan masuk outbox. Jika transaksi SQL commit, event dijamin 100% tersimpan dan siap dipublikasikan ke Kafka!

6. Production War Stories & Anti-Patterns

War Story: E-Commerce Kehilangan Sinkronisasi Saldo Akibat Dual-Write
Sebuah startup fintech mengeksekusi pendebetan saldo pengguna di database SQL dan kemudian memanggil event broker Redis Pub/Sub untuk mentransfer uang ke mitra bank.

Saat jaringan cloud mereka mengalami lonjakan sesaat (*Network Blip*), 140 transaksi berhasil memotong saldo di SQL, namun gagal mengirimkan sinyal event transfer ke broker.

Pelanggan mengamuk karena uang mereka terpotong tanpa adanya pengiriman dana ke tujuan!

Solusi: Mengimplementasikan Transactional Outbox Pattern dengan Idempotency Consumer, memastikan tidak ada satu pun rupiah yang hilang akibat kegagalan transmisi jaringan.

7. Kuis Uji Pemahaman: Domain-Driven Design

1. Apa perbedaan mendasar antara 'Entity' dan 'Value Object' di dalam Tactical Domain-Driven Design?
A. Entity disimpan di database, sedangkan Value Object hanya ada di memori
B. Entity memiliki identitas unik (ID) yang konsisten lintas waktu, sedangkan Value Object bersifat immutable dan kesamaannya ditentukan murni oleh nilai atributnya
C. Value Object hanya bisa dibuat dalam bahasa Java
2. Mengapa Transactional Outbox Pattern menjadi standar industri untuk mempublikasikan event pada arsitektur Event-Driven?
A. Karena dapat menggantikan fungsi database utama
B. Menjamin konsistensi atomik antara penyimpanan data bisnis dan pengiriman pesan event ke message broker (mengeliminasi The Dual-Write Problem)
C. Untuk mempercepat kecepatan browser merender CSS
