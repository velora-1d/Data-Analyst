Fase 14: Git Internals: Di Balik Perintah (Object Model & DAG)

Membongkar apa yang sesungguhnya terjadi di dalam folder .git/: sistem file berbasis konten (Content-Addressable Key-Value Store), dekonstruksi 4 tipe objek (Blob, Tree, Commit, Tag), mekanika percabangan Three-Way Merge vs Rebase, dan penyelamatan commit hilang melalui git reflog.

1. Model Mental: Git Bukan Sistem Penyimpan Delta/Diff!

Mitos terbesar seputar Git adalah anggapan bahwa Git menyimpan berkas sebagai "perubahan baris per baris (diff delta)" seperti SVN jadul.

Definisi Sejati Git Menurut Linus Torvalds
Git pada dasarnya adalah Content-Addressable Key-Value Store sederhana, yang dilapisi antarmuka Version Control System di atasnya.

Setiap file disimpan utuh sebagai snapshot yang dikompresi menggunakan algoritma zlib. Kunci (Key) untuk mengakses file tersebut adalah hash SHA-1 (40 karakter heksadesimal) dari konten berkas tersebut.

Jika dua file di folder berbeda memiliki isi yang 100% identik, Git hanya menyimpannya SATU KALI SAJA di disk.

2. Empat Tipe Objek Inti di Dalam .git/objects/

Objek 1
Blob (Binary Large Object)
Hanya menyimpan byte data mentah berkas. Tidak menyimpan nama file atau hak akses file!
Objek 2
Tree Object
Mewakili struktur direktori folder: memetakan nama file, izin Linux (100644), dan hash pointer ke blob.
Objek 3
Commit Object
Menunjuk ke satu root Tree, parent commit SHA, nama author, timestamp, dan commit message.
Objek 4
Annotated Tag
Pointer permanen ke commit tertentu dengan pesan rilis dan tanda tangan digital GPG.

4. Apa Sebenarnya Sebuah "Branch" di Git?

Branch Hanyalah File Teks 41-Byte!
Banyak pengembang mengira membuat branch baru adalah operasi mahal yang menduplikasi seluruh kode proyek.

Kenyataan di Balik Layar: Di Git, sebuah branch hanyalah file teks kecil berukuran 41 byte di dalam .git/refs/heads/nama-branch, yang berisi satu baris string hash commit 40 karakter!

Membuat branch baru (git branch fitur-baru) hanya membutuhkan waktu kurang dari 1 milidetik karena Git hanya menulis 40 karakter teks ke disk!

5. Three-Way Merge vs Rebase: Kapan Harus Digunakan?

Fitur Rekayasa Three-Way Merge (git merge) Rebase (git rebase)
Mekanisme Mencari Lowest Common Ancestor (LCA), lalu membuat 1 commit baru khusus (*Merge Commit*) dengan 2 parent. Memutar ulang (replay) commit cabang Anda satu per satu di atas ujung cabang target. Menciptakan SHA hash baru!
Bentuk Riwayat Non-linear (Terlihat cabang mencuat dan menyatu kembali). Menjaga konteks waktu asli. Linear sempurna (Satu garis lurus bersih seperti jalan tol).
Integritas History 100% aman dan tidak pernah mengubah commit yang sudah ada. Menulis ulang sejarah (Rewrites History)!
Aturan Emas (Golden Rule) Aman digunakan di cabang mana pun. DILARANG KERAS melakukan rebase pada cabang publik bersama (seperti main)!

6. Penyelamatan Bencana: Mengembalikan Commit Hilang via git reflog

Pernahkah Anda panik karena tidak sengaja menjalankan perintah git reset --hard HEAD~3 atau menghapus branch penting sebelum di-merge?

Cara Menyelamatkan Kode yang Hilang
# 1. Buka buku harian pergerakan pointer HEAD lokal Anda:
git reflog

# Output akan menampilkan seluruh jejak HEAD, termasuk commit yang terhapus:
# 74bd7ed HEAD@{0}: reset: moving to HEAD~3
# 3e48e8b HEAD@{1}: commit: feat: kode penting yang hilang!

# 2. Kembalikan branch atau buat branch baru dari hash yang hilang tersebut:
git checkout -b branch-selamat 3e48e8b

Fakta Git: Objek yang "hilang" sebenarnya tidak langsung dihapus dari harddisk. Objek tersebut tetap berada di folder .git/objects/ sebagai Dangling Commit selama 30 hingga 90 hari sebelum dibersihkan oleh git gc!
