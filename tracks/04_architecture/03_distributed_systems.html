Modul 15: Desain Sistem Terdistribusi & CAP/PACELC Theorem

Membedah prinsip dasar rekayasa sistem terdistribusi berskala global: 8 Ilusi Jaringan, kebenaran mutlak Teorema CAP vs PACELC, kalkulasi konsensus Quorum Leaderless (R + W > N), serta pemisahan arsitektur CQRS dengan Event Sourcing.

1. Delapan Ilusi Sistem Terdistribusi (The 8 Fallacies)

L. Peter Deutsch dan James Gosling merumuskan 8 asumsi salah yang sering dibuat oleh developer saat berpindah dari sistem monolitik ke sistem terdistribusi:

  1. "Jaringan selalu andal dan tidak pernah putus." (Kenyataan: Kabel putus, router crash, AWS availability zone mati).
  2. "Latensi jaringan adalah nol." (Kenyataan: Kecepatan cahaya di kabel fiber optik memakan waktu 100ms lintas benua).
  3. "Bandwidth tidak terbatas."
  4. "Jaringan aman."
  5. "Topologi jaringan tidak pernah berubah."
  6. "Hanya ada 1 administrator sistem."
  7. "Biaya transportasi data adalah nol."
  8. "Jaringan bersifat homogen."

2. Teorema CAP: Hukum Fisika Sistem Terdistribusi

Dirumuskan oleh Eric Brewer, Teorema CAP menyatakan bahwa dalam sistem penyimpanan data terdistribusi, Anda hanya dapat memilih maksimal dua dari tiga jaminan berikut:

C
Consistency
Setiap operasi baca (Read) menerima data penulisan (Write) paling mutakhir atau menghasilkan error.
A
Availability
Setiap request yang masuk selalu menerima respons sukses tanpa kegagalan (walau datanya mungkin sedikit usang).
P
Partition Tolerance
Sistem tetap dapat beroperasi meskipun terjadi pemutusan kabel jaringan antar server node di data center.
Mengapa "Memilih CA Tanpa P" Adalah Mitos?
Di dunia nyata, Partisi Jaringan (P) adalah fakta fisik yang tidak bisa dihindari. Kabel fiber laut bisa putus kapan saja.

Oleh karena itu, pilihan nyata bagi seorang arsitek sistem ketika jaringan terbelah (Partition) hanyalah:
  • Pilih CP (Consistency): Tolak atau tunda request pengguna demi memastikan data tidak pernah bertabrakan (contoh: Transfer Uang Bank, Google Spanner).
  • Pilih AP (Availability): Terima penulisan pengguna di node mana pun yang masih hidup, dan sinkronkan data nanti secara bertahap (*Eventual Consistency*, contoh: Like Instagram, Keranjang Belanja Amazon).

3. Teorema PACELC: Apa yang Terjadi Saat Jaringan Normal?

Kelemahan Teorema CAP adalah teorema tersebut hanya menjelaskan kondisi saat terjadi partisi jaringan (bencana). Daniel Abadi memperluasnya menjadi Teorema PACELC:

Rumus PACELC
Jika terjadi PARTISI (P):
    Pilih antara AVAILABILITY (A) atau CONSISTENCY (C)
ELSE (E) saat kondisi jaringan NORMAL:
    Pilih antara LATENCY (L) atau CONSISTENCY (C)
Database Klasifikasi PACELC Karakteristik Operasional
Apache Cassandra / DynamoDB PA / EL Saat partisi pilih Available; saat normal utamakan Latensi super rendah daripada konsistensi ketat.
MongoDB / PostgreSQL Replica PC / EC Selalu mengutamakan Konsistensi data, mengorbankan ketersediaan dan latensi baca jika replika tertinggal.

4. Matematika Quorum Konsensus: R + W > N

Pada sistem tanpa pemimpin terpusat (*Leaderless Replicas* seperti arsitektur Amazon Dynamo), konsistensi baca dan tulis diatur oleh formula Quorum:

Hukum Overlapping Quorum
Misalkan total replika node: N = 5:
• W = Jumlah node yang wajib mengonfirmasi sebelum Write dinyatakan sukses.
• R = Jumlah node yang wajib dibaca saat request Read.

Jika R + W > N (misal: W = 3, R = 3, total = 6 > 5):
Berdasarkan prinsip lubang merpati (Pigeonhole Principle), pasti ada minimal 1 node yang masuk ke dalam irisan grup baca dan tulis secara bersamaan! Dengan membandingkan nomor versi data, client dijamin 100% selalu membaca data paling mutakhir (*Strong Consistency*)!

5. Paradigma CQRS & Event Sourcing

CQRS (Command Query Segregation)
• Memisahkan jalur penulisan data (Command: Insert/Update dengan validasi ketat) dari jalur pembacaan (Query: Model denormalisasi cepat).
• Jalur baca bisa di-scale out menggunakan Elasticsearch / Read Replicas tanpa membebani database utama.
Event Sourcing (Buku Besar Abadi)
• Jangan simpan state akhir mutabel (seperti saldo = 50000).
• Simpan seluruh riwayat kejadian secara append-only: [AkunDibuka, SaldoDitambah 100k, SaldoDitarik 50k].
• Keuntungan: Audit log 100% akurat dan kemampuan Time Travel Debugging (memutar ulang state sistem ke tanggal berapa pun di masa lalu).

6. Production War Stories & Anti-Patterns

War Story: Clock Skew Menghilangkan Data di Kluster Cassandra
Sebuah bank digital menggunakan Cassandra dengan resolusi konflik default Last-Write-Wins (LWW) berbasis timestamp NTP server lokal.

Salah satu server mengalami kerusakan sinkronisasi waktu dan jam internalnya berlari 10 detik lebih cepat ke masa depan (*Clock Skew*).

Dampak: Setiap data yang ditulis oleh server rusak tersebut memiliki timestamp yang jauh lebih tinggi daripada server lain. Ketika user melakukan update data terbaru di server normal beberapa detik kemudian, Cassandra mengabaikan update tersebut dan menganggap data lama dari server rusak sebagai data yang lebih mutakhir!

Solusi: Gunakan Vector Clocks / Lamport Timestamps untuk pelacakan kausalitas logis alih-alih jam dinding fisik (Wall Clock), atau gunakan hardware GPS Atomic Clock seperti Google TrueTime Spanner.
