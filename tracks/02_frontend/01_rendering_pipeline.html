Modul 07: Browser Rendering Pipeline & The Event Loop

Bagaimana peramban web modern (Chromium Blink, WebKit, Gecko) mengubah teks mentah HTML/CSS menjadi piksel visual berkecepatan 60 FPS (16.6ms per frame): dari Critical Rendering Path, Layout Reflow, GPU Layer Compositing, hingga mikro-arsitektur JavaScript Event Loop.

1. Matematika Frame Budget 16.6ms (Standar 60 FPS)

Monitor standar bekerja pada frekuensi penyegaran (refresh rate) 60 Hz, yang berarti monitor menggambar ulang seluruh piksel di layar sebanyak 60 kali setiap detik.

Hukum 16.6 Milliseconds Budget
1.000 ms / 60 frames = 16.66 ms per frame.

Namun, browser memiliki housekeeping internal (overhead OS dan komposisi GPU) sekitar 6 ms. Artinya, total waktu yang Anda miliki untuk menjalankan JavaScript, menghitung CSS style, dan melakukan layout hanyalah sekitar 10 ms!

Jika kode JavaScript Anda memakan waktu 20 ms, browser akan melewatkan 1 frame refresh (Dropped Frame / Jank). Layar akan terlihat patah-patah dan animasi terasa tersendat bagi pengguna.

2. The Critical Rendering Path (CRP)

Ketika browser menerima respons byte HTML dari server, data mengalir melalui 6 tahap deterministik berurutan:

Tahap 1
DOM Tree
Bytes → Characters → Tokens → Nodes → Document Object Model
Tahap 2
CSSOM Tree
Parsing CSS rules → Cascading Selector Matching → CSS Object Model
Tahap 3
Render Tree
Gabungan DOM + CSSOM (mengabaikan display: none dan <head>)
Tahap 4
Layout (Reflow)
Kalkulasi geometri presisi: koordinat (x, y), lebar, tinggi tiap node di layar
Tahap 5
Paint (Raster)
Mengisi piksel visual: warna teks, borders, background, shadows ke memory buffer
Tahap 6
Compositing
Layer dikirim ke GPU VRAM untuk digabungkan dan ditampilkan di monitor

3. Pemicu Pipeline: Layout Reflow vs Repaint vs Composite

Kunci utama optimasi performa frontend adalah memahami operasi mana yang memaksa browser mengulang tahap kalkulasi:

Tingkat Biaya Tahapan Yang Dipicu Contoh Properti CSS Dampak Performa
Sangat Mahal Reflow (Layout) + Repaint + Composite width, height, margin, padding, left, top, fontSize CPU intensif. Memicu kalkulasi ulang geometri seluruh elemen turunan di halaman!
Sedang Repaint + Composite (Lewati Reflow) color, background-color, box-shadow, border-color, visibility Geometri tidak berubah, namun GPU harus menggambar ulang piksel warna ke memori.
Sangat Cepat Hanya Composite (Lewati Reflow & Paint!) transform: translate3d(), opacity Zero CPU Reflow! Dihitung langsung oleh GPU Hardware Acceleration pada thread Compositor. 60 FPS terjamin.

4. Bahaya Layout Thrashing (Forced Synchronous Layout)

Secara default, browser sangat cerdas: browser mengantrekan perubahan style DOM dan mengeksekusinya secara batch sekaligus di akhir frame.

Namun jika Anda membaca properti geometri geometris (seperti offsetHeight, clientWidth, getBoundingClientRect) tepat setelah mengubah style di dalam sebuah loop, Anda memaksa browser melakukan Forced Synchronous Layout (Layout Thrashing)!

Kode Berbahaya: Layout Thrashing
// Browser dipaksa reflow 1000 kali berturut-turut!
const boxes = document.querySelectorAll('.box');

boxes.forEach(box => {
    // 1. BACA Geometri (Forces immediate Reflow!)
    const currentHeight = box.offsetHeight; 
    
    // 2. TULIS Style (Invalidates Layout!)
    box.style.height = (currentHeight + 10) + 'px';
});
Kode Bersih: Pisahkan Read & Write
// 1. Kumpulkan semua READ terlebih dahulu (1 kali Reflow)
const boxes = document.querySelectorAll('.box');
const heights = Array.from(boxes).map(b => b.offsetHeight);

// 2. Lakukan semua WRITE secara batch
requestAnimationFrame(() => {
    boxes.forEach((box, i) => {
        box.style.height = (heights[i] + 10) + 'px';
    });
});

5. Anatomi JavaScript Event Loop: Microtasks, rAF & Macrotasks

JavaScript di browser adalah bahasa Single-Threaded. Bagaimana JS dapat menangani event klik, request API jaringan, dan animasi secara bersamaan tanpa membekukan layar? Jawabannya adalah Event Loop.

Siklus 1 Putaran Event Loop Browser (Frame Turn)
1. Call Stack (Sync)
2. Flush All Microtasks
3. requestAnimationFrame
4. Render (Layout/Paint)
5. One Macrotask
Urutan Prioritas Eksekusi Event Loop:
Synchronous Code > Microtasks (Durasinya dihabiskan sampai kosong) > rAF > Render Opportunity > Tepat 1 Macrotask.

6. Uji Analisis Antrean: Tebak Urutan Output Console

Perhatikan potongan kode wawancara rekayasa sistem tingkat senior berikut:

Event Loop Priority Puzzle
console.log('1: Synchronous Awal');

setTimeout(() => {
    console.log('2: Macrotask (setTimeout)');
}, 0);

Promise.resolve().then(() => {
    console.log('3: Microtask 1');
}).then(() => {
    console.log('4: Microtask 2');
});

requestAnimationFrame(() => {
    console.log('5: rAF Callback');
});

console.log('6: Synchronous Akhir');
Urutan Output Sebenarnya di Browser:
1: Synchronous Awal
6: Synchronous Akhir
3: Microtask 1        <-- Microtask queue dikuras habis segera setelah stack kosong!
4: Microtask 2        <-- Chained Promise dijalankan sebelum browser menyentuh antrean lain
5: rAF Callback       <-- Dijalankan tepat sebelum browser melakukan paint piksel
2: Macrotask (setTimeout) <-- Macrotask dieksekusi di putaran event loop berikutnya!

7. Production War Story: Bencana Infinite Microtask Loop

War Story: Tab Browser Hang Total Akibat queueMicrotask Recursion
Seorang developer junior ingin memproses 500.000 data array tanpa memblokir UI. Ia menggunakan rekursi Promise:
function process() { queueMicrotask(process); }

Apa yang terjadi? Layar browser langsung freeze putih seketika! User tidak bisa mengklik tombol apa pun atau melakukan scroll.

Penyebab: Spesifikasi W3C menyatakan bahwa Event Loop TIDAK AKAN PERNAH beralih ke tahap Render atau Macrotask sebelum Microtask Queue benar-benar KOSONG. Karena queueMicrotask terus menambahkan tugas baru tanpa henti, browser kelaparan (*Microtask Starvation*) dan tidak pernah sempat merender layar!

Solusi Industri: Gunakan Macrotask (setTimeout) atau rAF untuk me-yield kontrol kembali ke UI thread:
await new Promise(requestAnimationFrame);
