Modul 25: Git Internals & Data Recovery Tingkat Lanjut

Puncak penguasaan sistem kontrol versi: membedah perintah tingkat rendah (Plumbing API), merakit objek Commit dan Tree secara manual tanpa perintah git commit, arsitektur kompresi Packfiles, serta bedah pembersihan riwayat commit yang terkontaminasi file raksasa via git filter-repo.

1. Porcelain Commands vs Plumbing Commands

Git membagi seluruh perintahnya menjadi dua tingkatan:

Porcelain (Antarmuka Pengguna Ramah)
Perintah tingkat tinggi yang kita gunakan sehari-hari:
git add, git commit, git checkout, git merge, git log.
Perintah ini membungkus puluhan operasi rumit di baliknya menjadi 1 kata yang mudah dipahami manusia.
Plumbing (Perintah Mesin Tingkat Rendah)
Panggilan sistem internal yang memanipulasi objek database Git secara langsung:
git hash-object, git cat-file, git write-tree, git commit-tree, git update-ref.

2. Lab Hands-on: Membuat Commit Manual Murni Menggunakan Plumbing

Tahukah Anda bahwa kita dapat membuat commit resmi di Git tanpa pernah mengetikkan git add atau git commit? Mari kita buktikan:

Terminal Eksekusi Plumbing
# 1. Buat Blob dari string mentah dan simpan ke .git/objects/
$ BLOB_SHA=$(echo "Kode rahasia versi 1" | git hash-object -w --stdin)
# Output: e69de29bb2d1d6434b8b29ae775ad8c2e48c5391

# 2. Daftarkan blob ke staging index sementara:
$ git update-index --add --cacheinfo 100644 $BLOB_SHA rahasia.txt

# 3. Tulis pohon direktori (Tree Object) dari index:
$ TREE_SHA=$(git write-tree)
# Output: 040000... (Tree Hash)

# 4. Buat Commit Object yang menunjuk ke Tree tersebut:
$ COMMIT_SHA=$(echo "feat: commit manual murni via plumbing" | git commit-tree $TREE_SHA)

# 5. Pasang branch baru ke commit tersebut:
$ git update-ref refs/heads/cabang-manual $COMMIT_SHA

# SELESAI! Branch dan commit resmi tercipta sempurna di Git DAG!

3. Arsitektur Packfiles & Delta Compression

Jika Git menyimpan setiap versi file sebagai blob utuh, mengapa folder .git/ tidak membengkak menjadi puluhan gigabyte? Jawabannya adalah Packfiles:

Bagaimana git gc Mengompresi Objek?
Ketika Anda menjalankan git gc (Garbage Collection) atau saat melakukan push/pull:

1. Git mengumpulkan ratusan file objek terpisah (Loose Objects).
2. Git mencari file-file yang memiliki kemiripan nama dan konten.
3. Git menyimpan versi terbaru secara utuh, dan menyimpan versi-versi sebelumnya hanya sebagai perbedaan biner (Delta Compression) di dalam satu file berkas .pack raksasa!
4. Berkas indeks .idx dibuat untuk memungkinkan pencarian biner sub-milidetik ke dalam packfile tersebut.

4. Menghapus File Raksasa dari Sejarah Git (git filter-repo)

Kesalahan fatal yang sering dilakukan developer adalah tidak sengaja melakukan commit file data SQLite atau CSV berukuran 500 MB, lalu di commit berikutnya file tersebut dihapus (git rm).

Kenapa git clone Tetap Berat Meskipun File Sudah Dihapus?
Meskipun file sudah dihapus dari branch terbaru, blob 500 MB tersebut masih tertanam abadi di dalam riwayat commit masa lalu! Siapa pun yang melakukan git clone tetap dipaksa mengunduh seluruh 500 MB tersebut.

Solusi Baku: Tulis Ulang DAG Sejarah via git filter-repo
git filter-repo --invert-paths --path database_raksasa.db
Perintah ini memotong seluruh referensi blob tersebut dari setiap commit di masa lalu dan menghitung ulang seluruh hash commit secara bersih.

5. Pemulihan Reflog Tingkat Lanjut

git reflog bukan hanya untuk mengembalikan commit yang di-reset. Anda dapat menggunakannya untuk melacak:

  • Rebase yang Berantakan: Mengembalikan branch ke posisi sebelum rebase: git reset --hard ORIG_HEAD atau via nomor index reflog git reset --hard HEAD@{4}.
  • Branch yang Dihapus Tidak Sengaja: git branch nama-lama HEAD@{2} seketika menghidupkan kembali branch yang terhapus!

6. Production War Stories & Anti-Patterns

War Story: Ukuran Repositori Membengkak Menjadi 18 GB Akibat Video Demo
Sebuah tim frontend menambahkan video demo produk berukuran 200 MB ke dalam repositori. Di setiap sprint mingguan, video tersebut diperbarui dengan versi baru.

Dalam 1 tahun, ukuran repositori Git melonjak dari 150 MB menjadi 18 GB! Proses CI/CD di GitHub Actions menjadi sangat lambat (memakan waktu 15 menit hanya untuk git checkout).

Solusi: Menggunakan Git LFS (Large File Storage) untuk file biner besar (video, model AI, database dump). File biner disimpan di server S3 terpisah, dan Git hanya menyimpan pointer teks kecil berukuran 130 byte di dalam tree repository!
