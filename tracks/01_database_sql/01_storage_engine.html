Apa Ini Sebenarnya?

Storage engine adalah juru tulis fisik database yang bertugas mengukir data dari memori RAM ke lempengan harddisk atau SSD dalam bentuk lembaran blok halaman (pages).

Masalah Nyata Apa yang Diselesaikan?

Jika data ditulis sembarangan tanpa struktur, komputer harus memutar seluruh piringan disk berulang kali yang membuat server database menjadi sangat lambat dan cepat rusak.

Analogi Kehidupan Sehari-Hari

Ibarat buku ensiklopedia tebal dengan pembatas bab: alih-alih melempar kertas acak ke lantai, juru arsip menaruh tiap lembar secara alfabetis sehingga bisa dibuka tepat dalam 3 kali balik halaman (B-Tree).

Kapan Kita Memakainya?

Dibutuhkan saat data toko Anda bertambah dari ribuan menjadi jutaan transaksi, dan Anda ingin memastikan waktu simpan data tetap instan di bawah 5 milidetik.

Modul 04: Database Storage Engine & Struktur B-Tree

Membedah bagaimana basis data relasional menyimpan miliaran record di atas piringan magnetik atau NVMe SSD: dari arsitektur 4KB Slotted Page, eliminasi fragmentasi, traversal pencarian B+Tree, hingga Write-Ahead Logging (WAL) dan pemulihan crash ARIES.

1. Mengapa DBMS Bukan File Teks CSV atau JSON?

Banyak pengembang pemula membayangkan database bekerja seperti kumpulan file JSON atau CSV besar yang dibaca ke dalam memori. Namun, dalam sistem rekayasa perangkat lunak skala produksi, pendekatan file teks mentah akan runtuh seketika karena tiga batasan fundamental perangkat keras:

First Principles: Disk Block Alignment & Random Access
  1. Blok Sektor Perangkat Keras: Disk drive mekanis (HDD) dan NVMe SSD tidak dapat membaca atau menulis 1 byte secara terisolasi. Hardware membaca dan menulis dalam unit blok fisik: 512 byte (legacy) atau 4.096 byte (4KB Advanced Format). Setiap operasi I/O OS selalu memuat kelipatan 4KB ke RAM (Page Cache).
  2. Biaya Penggeseran Data (Data Shifting): Jika Anda menghapus baris ke-50 di tengah file CSV sepanjang 10 GB, OS harus membaca dan menulis ulang seluruh sisa file (9.9 GB) hanya untuk menutup celah byte yang kosong. Kompleksitasnya adalah O(N).
  3. Pencarian Tanpa Indeks: Mencari baris dengan customer_id = 4521 pada file teks mewajibkan pemindaian dari baris pertama hingga terakhir (Full Scan O(N)). Pada jutaan baris, query Anda akan memakan waktu puluhan detik.

Untuk mengatasi hal ini, seluruh database tingkat industri (SQLite, PostgreSQL, MySQL InnoDB, Oracle) membagi file database menjadi blok-blok berukuran tetap yang disebut Pages (halaman), biasanya berukuran 4096 byte (4 KB) agar selaras sempurna dengan arsitektur sistem operasi.

2. Anatomi 4KB Slotted Page

Tantangan terbesar sebuah page database adalah menampung baris-baris data yang panjangnya tidak seragam (variable-length). Sebuah nama pelanggan bisa terdiri dari 4 karakter atau 80 karakter. Jika record disimpan berurutan dari atas ke bawah, operasi UPDATE atau DELETE akan menimbulkan fragmentasi memori yang parah.

Solusi standar industri yang digunakan adalah arsitektur Slotted Page:

Visualisasi Alokasi Ruang Halaman 4.096 Byte (Slotted Page)
Page Header (8 atau 12 Byte)
Page Type Flag (0x0D), Cell Count, Offset Awal Cell Content, Freeblock Pointer
Offset 0x0000 - 0x000B
Cell Pointer Array (Tumbuh ke Bawah): [0x0FE8, 0x0FD0, 0x0FA4, ...] — Berisi offset 2-byte menuju posisi data
Ruang Bebas Tak Teralokasi (Unallocated Free Space Gap)
Menyusut saat record baru dimasukkan dari kedua sisi
Cell Content Area (Tumbuh ke Atas): Record data disimpan dari ujung terbawah (byte 4096) mundur ke atas.
Offset 0x1000 (Mundur)

Keunggulan Desain Slotted Page: Slot Pointer diurutkan secara teratur berdasarkan Primary Key (RowID). Ketika record diurutkan, database hanya menukar urutan offset 2-byte di Cell Pointer Array tanpa memindahkan byte data record yang berat di bagian bawah.

3. Tipe B-Tree Page dalam SQLite

Setiap page di dalam file database SQLite memiliki peran khusus yang ditandai oleh 1 byte flag pada offset pertama page (byte ke-0):

Flag (Hex) Nilai Desimal Tipe B-Tree Page Peran & Struktur Isi Data
0x0D 13 Leaf Table B-Tree Menyimpan baris data tabel sebenarnya (RowID + Serialized Column Payload).
0x05 5 Interior Table B-Tree Node cabang penunjuk (routing). Hanya menyimpan RowID dan pointer ke child page.
0x0A 10 Leaf Index B-Tree Menyimpan key indeks yang terurut beserta RowID baris yang dirujuk.
0x02 2 Interior Index B-Tree Cabang pohon indeks untuk navigasi pencarian binary search index range.
Kenapa B+Tree, Bukan Binary Search Tree (BST)?
Binary Search Tree memiliki Fan-out = 2 (setiap node hanya punya 2 anak). Untuk 1.000.000 data, kedalaman pohon mencapai log2(1.000.000) ≈ 20 level, yang berarti 20 kali seek disk I/O lambat!

B+Tree memiliki High Fan-out (ratusan hingga ribuan anak per node) karena 1 page 4KB dapat menampung ratusan pointer key. Dengan fan-out 500, pohon dengan kedalaman hanya 3 level dapat menampung:
500 × 500 × 500 = 125.000.000 record!
Artinya, pencarian data di antara 125 juta baris hanya memerlukan maksimal 3 kali pembacaan page dari disk.

4. B+Tree vs LSM-Tree: Pilihan Arsitektur Storage Engine Modern

Dalam lanskap rekayasa basis data modern, terdapat dua mazhab besar struktur data penyimpanan:

Karakteristik B+Tree (In-Place Update) LSM-Tree (Log-Structured Merge-tree)
Contoh DBMS SQLite, PostgreSQL, MySQL InnoDB, Oracle RocksDB, Apache Cassandra, ClickHouse, TiKV, ScyllaDB
Strategi Penulisan In-Place Update: Menimpa data pada page yang sama di disk. Append-Only: Selalu menulis ke MemTable (RAM) lalu flush SSTables ke disk.
Performa Write Lebih lambat (Random disk I/O, write amplification saat split page). Sangat Cepat: Sequential write tanpa seek disk acak.
Performa Read Sangat Cepat & Prediktif: O(log N) langsung via tree traversal. Lebih bervariasi (Memeriksa MemTable, SSTables, dibantu Bloom Filter).
Biaya Background Rendah (Hanya perlu VACUUM berkala). Tinggi (Proses Compaction latar belakang memakan CPU & Disk I/O).

5. Write-Ahead Logging (WAL) & Algoritma Pemulihan Crash ARIES

Bagaimana database menjamin sifat Durability (D) dalam ACID saat komputer mendadak mati atau kehilangan daya di tengah transaksi?

Aturan Sakral Storage Engine: The WAL Rule
"Tidak ada page data yang boleh ditulis ke disk sebelum catatan log transaksi (WAL) yang menjelaskan perubahan tersebut berhasil tersimpan permanen di media disk (fsync)."

Secara default, SQLite versi lama menggunakan Rollback Journal yang mengunci seluruh database saat penulisan (writers block readers). Sejak SQLite 3.7+, mode WAL (Write-Ahead Logging) menjadi standar industri:

Rollback Journal (Tradisional)
1. Penulis mengunci database secara eksklusif.
2. Page lama disalin ke database.db-journal.
3. Database utama dimodifikasi langsung.
4. Reader terblokir total selama proses commit.
Write-Ahead Log (WAL Modern)
1. Database utama tidak pernah diubah secara langsung.
2. Perubahan baru di-append ke database.db-wal.
3. Readers dan Writer bekerja bersamaan tanpa saling mengunci!
4. Proses Checkpointing memindahkan data WAL ke DB utama.

Algoritma Pemulihan Crash ARIES (Algorithms for Recovery and Isolation Exploiting Semantics)

Ketika database menyala kembali setelah crash, algoritma ARIES mengeksekusi 3 fase pemulihan berurutan:

  1. Analysis Phase: Memindai WAL dari checkpoint terakhir untuk mengidentifikasi transaksi mana yang aktif saat crash dan page mana yang kotor (dirty pages).
  2. Redo Phase (Repeating History): Memutar ulang seluruh perubahan log ke depan untuk mengembalikan state database persis seperti milidetik sebelum crash terjadi.
  3. Undo Phase: Membatalkan (rollback) seluruh transaksi yang belum sempat di-COMMIT saat crash terjadi, memastikan konsistensi data tetap murni.

6. Lab Hands-on: Membedah Byte Biner ecommerce.db

Mari buktikan teori di atas dengan langsung menginspeksi file basis data ecommerce.db yang ada di repositori kita menggunakan script terminal nyata:

PowerShell / Bash Command 
# Memeriksa 100 Byte Header Database SQLite dan Page Size:
powershell -Command "
\$bytes = [System.IO.File]::ReadAllBytes('database/ecommerce.db');
Write-Host 'Panjang File :' \$bytes.Length 'Bytes';
Write-Host 'Magic String :' ([System.Text.Encoding]::ASCII.GetString(\$bytes[0..15]));
Write-Host 'Page Size    :' ([System.BitConverter]::ToUInt16(\$bytes[17..16], 0)) 'Bytes';
Write-Host 'Tipe Page 1  : 0x' ('{0:X2}' -f \$bytes[100]);
"
Output Eksekusi Aktual dari ecommerce.db 
Panjang File : 118784 Bytes (29 Halaman x 4096 Byte)
Magic String : SQLite format 3 
Page Size    : 4096 Bytes
Tipe Page 1  : 0x05 (Interior Table B-Tree - Schema Root)
Bukti Empiris Byte Biner:
Terbukti secara empiris: 118.784 byte / 4.096 byte = persis 29 pages. Page 1 memiliki tipe 0x05 (Interior Table B-Tree) yang bertindak sebagai root tree untuk tabel master skema SQLite (sqlite_schema)!

7. Production War Stories & Anti-Patterns

War Story: Bencana Torn Write dan Cache Controller Berbohong
Sebuah startup e-commerce mengalami kerusakan data fatal saat listrik datacenter padam tiba-tiba. Setelah diinvestigasi, SSD controller consumer-grade yang mereka gunakan "berbohong" kepada OS: ketika OS mengirim perintah fsync(), drive mengonfirmasi bahwa data telah tertulis di flash storage, padahal data baru berada di volatile RAM cache SSD tanpa perlindungan baterai (Supercapacitor).

Saat daya putus, page 4KB hanya tertulis separuh (2048 byte), menghasilkan fenomena Torn Page yang merusak B-Tree checksum.

Solusi Industri: Gunakan Enterprise NVMe SSD dengan fitur Power Loss Protection (PLP) dan aktifkan PRAGMA synchronous = FULL atau EXTRA pada sistem keuangan sensitif.
