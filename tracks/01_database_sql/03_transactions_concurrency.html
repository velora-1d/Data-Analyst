Modul 06: Transaksi Database, 4 Anomali ANSI SQL & Concurrency Control

Pertahanan mutlak terhadap hilangnya uang nasabah, race condition checkout flash sale, dan saldo minus: membedah 4 anomali data ANSI SQL, Snapshot Isolation Write Skew, arsitektur Multi-Version Concurrency Control (MVCC), hingga orkestrasi Saga pada sistem terdistribusi.

1. Masalah Konkurensi: Saat Ribuan User Menyerbu Database

Jika database hanya melayani satu pengguna pada satu waktu (Single Thread), konsistensi data adalah hal yang sepele. Namun di dunia nyata, sistem e-commerce seperti Tokopedia atau Amazon melayani puluhan ribu request per detik (QPS) yang berusaha membaca dan memodifikasi baris data yang sama secara serentak.

Tanpa mekanisme Concurrency Control yang ketat, database akan mengalami bencana Race Condition: dua pembeli sama-sama membeli sisa 1 unit barang terakhir pada milidetik yang sama, menyebabkan stok barang menjadi -1 (Over-selling).

2. 4 Anomali Standar ANSI SQL 92

Standar internasional ANSI SQL mengklasifikasikan fenomena inkonsistensi data konkurensi menjadi 4 fenomena utama:

1. Dirty Read (Membaca Data Kotor/Palsu)

Transaksi A mengubah data namun belum COMMIT. Transaksi B membaca data perubahan tersebut. Tiba-tiba Transaksi A mengalami error dan melakukan ROLLBACK. Data yang dibaca Transaksi B menjadi "hantu" fiktif yang tidak pernah sah ada di database!

T1TX 1: UPDATE saldo = 10jtTX 2: Tunggu...
T2TX 1: Masih proses...TX 2: SELECT saldo → 10jt (DIRTY!)
T3TX 1: ROLLBACK! (Kembali 1jt)TX 2: Mengirim barang senilai 10jt!
2. Non-Repeatable Read (Fuzzy Read)

Transaksi A membaca baris pelanggan dengan saldo 5 juta. Selagi Transaksi A masih berjalan, Transaksi B melakukan UPDATE saldo menjadi 2 juta dan COMMIT. Ketika Transaksi A membaca ulang baris yang sama, nilainya mendadak berubah menjadi 2 juta di tengah-tengah transaksi!

3. Phantom Read (Baris Siluman)

Transaksi A menghitung jumlah transaksi: SELECT COUNT(*) WHERE status = 'Selesai' dan mendapatkan 100 baris. Bersamaan dengan itu, Transaksi B melakukan INSERT transaksi baru dan COMMIT. Saat Transaksi A membaca range yang sama, jumlah baris bertambah menjadi 101. Baris baru ini muncul layaknya "siluman".

4. Write Skew & Serialization Anomaly (Paradoks Dokter Jaga)

Studi Kasus Rumah Sakit: Aturan RS mensyaratkan "Minimal harus ada 1 dokter yang berjaga di malam hari". Saat ini ada 2 dokter jaga: Dokter Alice dan Dokter Bob.

Dokter Alice membuka aplikasi, melihat Bob sedang jaga, lalu mengajukan cuti (Alice off). Pada detik yang persis sama, Bob membuka aplikasi, melihat Alice sedang jaga, lalu mengajukan cuti (Bob off).

Kedua transaksi valid secara terisolasi, namun ketika keduanya COMMIT, rumah sakit tidak memiliki dokter jaga sama sekali! Inilah anomali Write Skew yang lolos di bawah isolasi Snapshot Isolation standard.

4. MVCC vs Two-Phase Locking (2PL)

Bagaimana database menerapkan isolasi tersebut di tingkat arsitektur perangkat lunak?

Two-Phase Locking (2PL Tradisional)
• Growing Phase: Transaksi meminta shared lock (S-Lock) untuk read dan exclusive lock (X-Lock) untuk write.
• Shrinking Phase: Lock dilepas setelah commit.
• Kelemahan Fatal: Readers memblokir Writers, dan Writers memblokir Readers! Menyebabkan deadlock dan antrean query macet pada sistem ber-traffic tinggi.
Multi-Version Concurrency Control (MVCC)
• Database menyimpan beberapa versi sekaligus dari baris data yang sama.
• Setiap transaksi membaca snapshot konsisten berdasarkan timestamp atau Transaction ID (xmin/xmax).
• Keunggulan Revolusioner: Readers TIDAK PERNAH memblokir Writers, dan Writers TIDAK PERNAH memblokir Readers!

5. Strategi Penguncian di Level Aplikasi: Pessimistic vs Optimistic Locking

Pessimistic Locking (SELECT ... FOR UPDATE)
Aplikasi mengasumsikan konflik pasti akan terjadi. Database mengunci baris secara eksklusif segera setelah baris dibaca:
BEGIN TRANSACTION;
SELECT stok FROM produk WHERE id = 101 FOR UPDATE;
UPDATE produk SET stok = stok - 1 WHERE id = 101;
COMMIT;

Kapan Digunakan: Kontensi sangat tinggi (kursi bioskop, tiket konser) di mana kegagalan transaksi tidak dapat ditoleransi.
Optimistic Concurrency Control (OCC - Versioning)
Aplikasi mengasumsikan konflik jarang terjadi. Baris dibaca tanpa lock sama sekali, namun dilengkapi kolom version INT:
-- 1. Baca data dan versi saat ini (misal version = 4):
SELECT stok, version FROM produk WHERE id = 101;

-- 2. Update secara atomik dengan syarat versi belum berubah:
UPDATE produk
SET stok = stok - 1, version = version + 1
WHERE id = 101 AND version = 4;

Jika rows_affected == 0, artinya ada transaksi lain yang mendahului! Aplikasi cukup me-retry transaksi secara otomatis. Bebas dari deadlock dan sangat scalable!

6. Transaksi Terdistribusi & Pola Saga

Dalam arsitektur Microservices di mana Service Pesanan, Service Pembayaran, dan Service Gudang memiliki database terpisah, transaksi ACID lokal tidak lagi bisa digunakan.

Protokol tradisional Two-Phase Commit (2PC) memiliki kelemahan kritis: jika Coordinator mati di tengah jalan, seluruh database downstream terkunci tanpa batas waktu (Blocking Protocol).

Pola Saga: Rangkaian Transaksi Lokal & Kompensasi
Saga memecah transaksi terdistribusi menjadi serangkaian transaksi lokal yang dieksekusi berurutan:
  1. Order Service: Buat pesanan status PENDING.
  2. Payment Service: Debet kartu kredit pelanggan.
  3. Inventory Service: Kurangi stok di gudang.
Jika pada langkah ke-3 inventaris habis, Saga memicu Compensating Transaction (Rollback Semantik):
  • Payment Service membatalkan tagihan (Refund).
  • Order Service mengubah status pesanan menjadi CANCELLED.

7. Production War Stories & Anti-Patterns

War Story: Bencana Double Refund FinTech Senilai 2.4 Miliar
Sebuah dompet digital mengalami eksploitasi di mana pengguna sengaja menekan tombol "Refund" 10 kali secara paralel menggunakan bot multi-threading.

Aplikasi menggunakan query:
if (status == 'SUCCESS') { refundMoney(); updateStatus('REFUNDED'); }
Karena transaksi berjalan di bawah isolasi READ COMMITTED tanpa Pessimistic Lock atau CAS Versioning, ke-10 thread membaca status == 'SUCCESS' secara bersamaan sebelum thread pertama sempat meng-update status! Akibatnya dana di-refund 10 kali untuk 1 transaksi.

Perbaikan: Menambahkan Idempotency Key unik pada setiap permintaan refund dan menggunakan Optimistic CAS atomic conditional update.
