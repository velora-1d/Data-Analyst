Modul 05: Indexing Strategy, B-Tree Traversal & EXPLAIN QUERY PLAN

Transformasi query yang lambat menjadi secepat kilat: membedah cara kerja internal B-Tree Index Sekunder, aturan absolut Leftmost Prefix pada Compound Index, eliminasi disk seek tabel via Covering Index, dan rekayasa query SARGable anti-full scan.

1. Anatomi B-Tree Index Sekunder

Ketika Anda mengeksekusi CREATE INDEX idx_pesanan_tgl ON pesanan(tanggal_pesanan);, apa yang sebenarnya terjadi di dalam disk storage database?

Database tidak sekadar menduplikasi baris tabel. Database membangun pohon B-Tree terpisah (Secondary B-Tree). Pada B-Tree sekunder ini:

  • Key: Nilai kolom yang diindeks (misalnya tanggal_pesanan), tersusun rapi secara terurut (sorted).
  • Payload: Pointer penunjuk balik berupa RowID (Primary Key) dari baris tabel utama.
Dua Langkah Pencarian Index Lookup (Index Seek + Table Seek)
Ketika query menjalankan SELECT total_bayar FROM pesanan WHERE tanggal_pesanan = '2024-03-01':
  1. Langkah 1 (Index Seek): Database mencari key '2024-03-01' di B-Tree Index secara binary search dengan kompleksitas O(log N), lalu menemukan RowID = 1042.
  2. Langkah 2 (Table Random Seek / Bookmark Lookup): Database mengambil RowID 1042, lalu melompat ke B-Tree Tabel Utama untuk mengambil kolom total_bayar. Langkah kedua ini membutuhkan random I/O disk tambahan jika kolom tidak ada di dalam index!

2. Aturan Emas Leftmost Prefix pada Compound Index

Sebuah Compound Index (indeks gabungan beberapa kolom) dibuat untuk mengoptimasi query multi-kondisi, contohnya:

DDL Compound Index
CREATE INDEX idx_order_comp ON pesanan(status_pesanan, tanggal_pesanan, total_bayar);

Bagaimana database menyusun data dalam compound index ini? Pahami Analogi Buku Telepon Klasik:

Analogi Buku Telepon: (Nama Belakang, Nama Depan)
Buku telepon dicetak terurut abjad berdasarkan Nama Belakang terlebih dahulu, baru kemudian Nama Depan.
  • Jika Anda mencari "Siapa saja yang bernama belakang 'Nawawi'?" → Sangat Cepat (Index Digunakan).
  • Jika Anda mencari "Siapa yang bernama belakang 'Nawawi' dan nama depan 'Mahin'?" → Sangat Cepat (Index Digunakan Penuh).
  • Namun jika Anda mencari "Siapa saja yang nama depannya 'Mahin' tanpa peduli nama belakangnya?" → Anda terpaksa membalik lembar demi lembar dari halaman 1 sampai akhir buku (Full Scan O(N)) karena nama depan tersebar acak di setiap nama belakang yang berbeda!
Aturan Leftmost Prefix: Indeks (A, B, C) hanya dapat melayani query yang memfilter (A), (A, B), atau (A, B, C). Indeks ini TIDAK DAPAT DIGUNAKAN oleh query yang hanya memfilter (B) atau (C)!

3. Selektivitas & Kardinalitas Index

Apakah kita harus mengindeks semua kolom? TIDAK! Query Optimizer memutuskan apakah akan menggunakan index atau melakukan Full Table Scan berdasarkan rasio Selektivitas (Kardinalitas):

Rumus Selektivitas Index
Rasio Selektivitas = COUNT(DISTINCT kolom) / COUNT(*)
Mengapa Mengindeks Kolom Boolean (Status Aktif) Sering Diabaikan Optimizer?
Jika sebuah tabel pelanggan memiliki 1.000.000 baris dengan kolom is_active BOOLEAN di mana 90% bernilai TRUE dan 10% bernilai FALSE:

Rasio selektivitas kolom hanya 2 / 1.000.000 = 0.000002 (sangat buruk!). Jika query mencari WHERE is_active = TRUE, membaca B-Tree lalu melakukan 900.000 kali random seek ke tabel utama jauh lebih lambat daripada membaca file tabel secara berurutan (Sequential Scan) dari awal sampai akhir!

Solusi: Gunakan Partial Index:
CREATE INDEX idx_inactive ON pelanggan(email) WHERE is_active = 0;

4. Membedah Makna Output EXPLAIN QUERY PLAN

Jangan pernah menebak-nebak kecepatan query Anda. Periksa rencana eksekusi compiler menggunakan perintah EXPLAIN QUERY PLAN:

BAHAYA: Full Table Scan 
QUERY PLAN
`--SCAN pesanan

Database membaca setiap halaman 4KB di tabel dari awal sampai habis. Kompleksitas O(N). Menyebabkan CPU 100% dan disk saturation di sistem produksi.

OPTIMAL: Index Search 
QUERY PLAN
`--SEARCH pesanan USING INDEX idx_tgl (tgl=?)

Database melompati jutaan baris langsung ke leaf page yang tepat menggunakan binary search tree. Kompleksitas O(log N). Latensi hanya 0.1ms.

5. Kekuatan Sakti Covering Index

Apa tingkat efisiensi tertinggi dalam indexing? Jawabannya adalah Covering Index.

Covering Index terjadi ketika seluruh kolom yang ada di klausa SELECT, WHERE, JOIN, dan ORDER BY sudah tercakup di dalam node leaf B-Tree Index itu sendiri!

Output Nyata Covering Index di SQLite:
QUERY PLAN
`--SEARCH pesanan USING COVERING INDEX idx_pesanan_status (status_pesanan=?)

Keuntungan 10x Lipat: Database tidak perlu melakukan disk seek ke tabel utama sama sekali! Seluruh data langsung diambil dari index leaf, memotong latensi I/O hingga 70-90%.

6. Desain Query SARGable (Search Argument Able)

Seringkali developer sudah membuat index dengan benar, namun index tersebut sama sekali tidak terpakai karena penulisan query yang melanggar kaidah SARGable:

Non-SARGable (Index Gugur → SCAN TABLE)
-- 1. Membungkus kolom dengan fungsi
WHERE strftime('%Y', tanggal_pesanan) = '2024'

-- 2. Wildcard di awal string
WHERE nama_pelanggan LIKE '%budi'

-- 3. Operasi aritmatika pada kolom
WHERE total_bayar + 10000 > 500000

-- 4. Implicit Type Conversion (Teks vs Angka)
WHERE nomor_hp = 6281234567
SARGable (Index B-Tree Aktif → SEARCH TABLE)
-- 1. Gunakan range comparison langsung
WHERE tanggal_pesanan >= '2024-01-01'
  AND tanggal_pesanan <  '2025-01-01'

-- 2. Wildcard hanya di akhir (Prefix Search)
WHERE nama_pelanggan LIKE 'budi%'

-- 3. Pindahkan kalkulasi ke sisi nilai konstan
WHERE total_bayar > 500000 - 10000

-- 4. Tipe data cocok persis
WHERE nomor_hp = '6281234567'
