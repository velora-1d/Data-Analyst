Fase 12: Autentikasi Modern, OAuth 2.0 PKCE & Keamanan API

Benteng pertahanan sistem backend: komparasi arsitektur Stateful Session (Redis) vs Stateless JWT, mekanisme rotasi token aman (Refresh Token Rotation), implementasi standar keamanan OAuth 2.0 Authorization Code with PKCE (RFC 9700), dan penutupan celah fatal OWASP Top 10 API Security (BOLA / IDOR).

1. Fondasi: Autentikasi vs Otorisasi

Banyak bug fatal berakar dari kerancuan antara dua konsep dasar ini:

  • Authentication (AuthN - Siapa Anda?): Memverifikasi identitas pengguna (Username/Password, Biometrik, Multi-Factor Authentication TOTP).
  • Authorization (AuthZ - Apa Hak Anda?): Memeriksa apakah identitas yang sudah terverifikasi tersebut memiliki izin untuk membaca atau menghapus resource tertentu (Role-Based Access Control - RBAC / Attribute-Based Access Control - ABAC).

2. Stateful Session (Redis) vs Stateless JWT

Stateful Session (Redis Clustered)
• Server membuat Session ID acak 128-bit dan menyimpannya di Redis.
• Dikirim ke browser via Cookie HttpOnly; Secure; SameSite=Strict.
• Kelebihan Luar Biasa: Instant Revocation! Jika akun dicuri atau admin menekan tombol "Logout All Devices", server cukup menghapus key di Redis dalam waktu 1 milidetik!
Stateless JWT (JSON Web Tokens)
• Berisi 3 bagian: Header.Payload.Signature yang ditandatangani secara kriptografis (HMAC SHA-256 / RSA-256).
• Server tidak perlu menyimpan state di database (Verifikasi tanda tangan matematika lokal O(1)).
• Kelemahan Fatal: Tidak Bisa Dibatalkan Sebelum Expired! Jika token dicuri penyerang, token tersebut tetap sah dipakai hingga masa berlakunya habis.

3. Refresh Token Rotation & Automatic Token Family Revocation

Bagaimana standar industri (RFC 9700) menyelesaikan kelemahan stateless JWT?

Pola Refresh Token Rotation (RTR)
1. Access Token (Umur Singkat: 15 Menit): Disimpan di memory JavaScript untuk otorisasi API request.
2. Refresh Token (Umur Panjang: 7 Hari): Disimpan di cookie HttpOnly terproteksi.
3. Setiap kali Access Token diperpanjang, REFRESH TOKEN LAMA OTOMATIS HANGUS dan server menerbitkan Refresh Token baru!

Automatic Breach Detection: Jika hacker mencuri Refresh Token dan mencoba menukarkannya, atau korban yang sah mencoba menukarkan Refresh Token lama yang sudah basi, server mendeteksi Token Reuse Anomaly dan seketika membatalkan SELURUH sesi keluarga token (Token Family Revocation)!

4. Standar Emas OAuth 2.0: Authorization Code with PKCE (RFC 9700)

Dahulu aplikasi Single-Page App (SPA) dan mobile menggunakan Implicit Grant. Pola ini resmi dilarang (deprecated) karena access token terekspos di URL hash fragment browser.

Standar wajib saat ini untuk seluruh aplikasi adalah PKCE (Proof Key for Code Exchange - diucapkan "Pixy"):

Langkah 1
Generate Verifier
Client membuat string acak kriptografis: code_verifier.
Langkah 2
SHA-256 Challenge
Client membuat hash: code_challenge = BASE64URL(SHA256(verifier)).
Langkah 3
Auth Request
Kirim code_challenge ke Auth Server untuk mendapatkan Auth Code.
Langkah 4
Token Exchange
Client menukar Auth Code + code_verifier asli. Server memvalidasi hash cocok sebelum memberikan Token!

5. Pertahanan OWASP API #1: BOLA (Broken Object Level Authorization) / IDOR

Kerentanan keamanan API paling mematikan dan paling sering dieksploitasi di dunia adalah BOLA (Broken Object Level Authorization), atau dikenal juga sebagai IDOR (Insecure Direct Object References).

Kode Rentan Celah BOLA / IDOR
// Hacker cukup mengganti angka ID pesanan di URL untuk mengintip faktur pelanggan lain!
app.get('/api/pesanan/:id', async (req, res) => {
    const pesanan = await db.query(
        'SELECT * FROM pesanan WHERE pesanan_id = ?', 
        [req.params.id]
    );
    res.json(pesanan);
});
Kode Aman: Verifikasi Kepemilikan (AuthZ Guard)
// Validasi apakah pesanan tersebut benar-benar milik user yang sedang terotentikasi!
app.get('/api/pesanan/:id', authMiddleware, async (req, res) => {
    const pesanan = await db.query(
        'SELECT * FROM pesanan WHERE pesanan_id = ? AND pelanggan_id = ?', 
        [req.params.id, req.user.pelanggan_id]
    );
    if (!pesanan) return res.status(404).json({ error: 'Tidak ditemukan' });
    res.json(pesanan);
});

6. Algoritma Pembatas Laju Akses (Rate Limiting)

Untuk mencegah brute force password dan serangan penolakan layanan (DDoS), API wajib dilindungi oleh middleware Rate Limiting:

  • Fixed Window Counter: Membagi waktu menjadi jendela 1 menit. Rentan terhadap lonjakan trafik di batas menit (Edge Burst).
  • Sliding Window Log / Counter: Menghitung rata-rata request bergerak dengan presisi tinggi di memori Redis.
  • Token Bucket / Leaky Bucket: Mengizinkan burst trafik sesaat hingga kapasitas bucket penuh, lalu mengalirkan request keluar dengan kecepatan konstan. Sangat cocok untuk API e-commerce!

7. Production War Stories & Anti-Patterns

War Story: Celah BOLA Membocorkan Rekam Medis 10 Juta Pasien
Sebuah aplikasi laboratorium klinik ternama meluncurkan fitur cetak hasil lab PDF secara online.

Endpoint yang dibuat adalah: GET /api/lab-reports/download?report_id=84021.
Pengembang mengandalkan autentikasi JWT yang valid, namun di dalam controller backend mereka lupa memverifikasi apakah report_id=84021 benar milik user yang sedang login!

Seorang peneliti keamanan mengganti angka report_id secara sekuensial (84020, 84019, ...) menggunakan skrip cURL sederhana dan berhasil mengunduh ribuan hasil rekam medis sensitif pasien lain secara bebas.

Pelajaran Berharga: Autentikasi (JWT valid) TIDAK BERARTI otorisasi aman! Selalu terapkan klausa WHERE id = :id AND user_id = :current_user di level query database atau gunakan UUID v4 acak yang tidak dapat ditebak.

8. Kuis Uji Pemahaman: Autentikasi & Keamanan API

1. Apa tujuan utama dari mekanisme PKCE (Proof Key for Code Exchange) dalam alur OAuth 2.0?
A. Mengurangi ukuran payload access token JWT
B. Mencegah intersepsi Authorization Code oleh aplikasi jahat di perangkat pengguna dengan mewajibkan verifikasi rahasia kriptografis (code_verifier)
C. Menghilangkan kebutuhan koneksi internet saat login
2. Manakah skenario di bawah ini yang merupakan contoh klasik dari celah keamanan BOLA (Broken Object Level Authorization)?
A. Penyerang menyisipkan karakter ' OR 1=1 -- ke dalam form login
B. Pengguna A yang sudah login berhasil mengunduh data faktur milik Pengguna B hanya dengan mengubah parameter ID pada URL /api/faktur/102 menjadi /api/faktur/101
C. Penyerang mengirimkan 1 juta request per detik hingga server crash
