Modul 11: Desain Arsitektur API: REST vs GraphQL vs gRPC

Membedah tiga gaya arsitektur antarmuka program aplikasi (API) paling dominan di industri perangkat lunak global: kematangan RESTful Richardson Model, fleksibilitas schema-driven GraphQL dengan mitigasi kueri N+1 DataLoader, serta efisiensi biner gRPC Protocol Buffers untuk inter-service microservices.

1. Tidak Ada "Satu API Untuk Semua Masalah"

Di industri perangkat lunak modern, memilih gaya API bukan soal tren atau selera pribadi, melainkan soal konteks arsitektur dan trade-off rekayasa:

  • Public & Mobile Web APIs: Mengutamakan standarisasi HTTP, kemudahan integrasi pihak ketiga, dan kemampuan caching CDN (Edge Caching). → REST.
  • Complex Client-Driven UIs: Mengutamakan fleksibilitas kueri, penghematan round-trip jaringan di aplikasi mobile, dan eliminasi over-fetching. → GraphQL.
  • Internal Microservices Back-to-Back: Mengutamakan throughput tinggi, latensi sub-milidetik, serialisasi biner super ringkas, dan kontrak tipe data yang ketat. → gRPC.

2. Standar Kematangan REST: Richardson Maturity Model

Banyak developer mengaku membuat "REST API", padahal kenyataannya mereka hanya membuat RPC (Remote Procedure Call) di atas HTTP dengan metode POST acak. Leonard Richardson merumuskan 4 tingkatan kematangan REST sejati:

Level 0
The Swamp of POX
1 endpoint URL (misal /api), seluruh aksi dikirim via POST dengan format custom XML/JSON.
Level 1
Resources (URI)
Entitas dipetakan ke URI unik tersendiri: /pesanan/101, /pelanggan/45.
Level 2
HTTP Verbs & Status
Menggunakan kata kerja semantik: GET (Read), POST (Create), PUT (Replace), DELETE, serta status 200, 201, 404.
Level 3
HATEOAS
Respons menyertakan hypermedia links (rel) yang memandu client ke aksi berikutnya yang diizinkan.
Kaidah Idempotensi HTTP (Idempotency)
Metode HTTP disebut Idempoten jika mengeksekusi request tersebut 1 kali atau 100 kali berturut-turut menghasilkan state akhir data di server yang persis sama:
  • Idempoten: GET, PUT (menimpa data pada ID yang sama), DELETE (menghapus ID yang sama), HEAD.
  • NON-Idempoten: POST (mengekseskusi POST 5 kali akan membuat 5 transaksi pesanan baru dan mendebet uang 5 kali!).

3. GraphQL Internals & Bencana N+1 Query

GraphQL (dikembangkan oleh Meta pada 2015) menyelesaikan dua masalah klasik REST:
1. Over-fetching: REST mengembalikan 50 field yang tidak dibutuhkan layar HP.
2. Under-fetching: Client harus menembak 3 endpoint berbeda (User → Pesanan → Rincian) hanya untuk merender 1 layar.

The Infamous N+1 Problem pada Resolver GraphQL
Jika client meminta daftar 100 pesanan beserta nama pelanggan pemiliknya:
query { orders { id customer { name } } }

Jika resolver tidak dirancang dengan hati-hati:
  1. Query 1: Database mengeksekusi SELECT * FROM pesanan LIMIT 100 (1 query).
  2. Query 2 s/d 101: Resolver customer dipanggil 100 kali secara terisolasi: SELECT * FROM pelanggan WHERE id = ? (N query!).
Total ada 101 query ke database hanya untuk 1 request pengguna!

Solusi Baku: DataLoader (Batching & Per-Request Caching)
DataLoader mengumpulkan seluruh 100 ID pelanggan di satu putaran Event Loop, lalu menembak 1 query efisien: SELECT * FROM pelanggan WHERE id IN (1, 2, 3, ... 100).

4. gRPC & Protocol Buffers: Komunikasi Biner Berkecepatan Tinggi

Ketika microservice saling bertukar data jutaan kali per detik, serialisasi dan parsing JSON berbasis teks menjadi beban CPU yang sangat besar. Google menciptakan gRPC dengan Protocol Buffers (Protobuf):

JSON Payload (Boros Teks: ~120 Bytes)
{
  "order_id": 10452,
  "customer_id": 89,
  "total_amount": 250000.50,
  "status": "PAID"
}
Protobuf Binary Payload (Hemat: ~22 Bytes!)
// Skema .proto:
message Order {
  int64 order_id = 1;
  int32 customer_id = 2;
  double total_amount = 3;
  string status = 4;
}
// Di-encode menjadi binary varints (6x lebih padat)

4 Pola Komunikasi gRPC:
1. Unary RPC: 1 Request → 1 Response (mirip REST biasa).
2. Server Streaming RPC: 1 Request → Aliran data berkelanjutan dari server.
3. Client Streaming RPC: Aliran data dari client (misal upload chunk video) → 1 Response.
4. Bidirectional Streaming RPC: Client dan server saling mengirim stream paralel tanpa henti.

5. Matriks Komparasi & Panduan Keputusan Arsitektur

Fitur Rekayasa REST API GraphQL gRPC
Format Serialisasi JSON (Teks) JSON (Teks) Protocol Buffers (Biner)
Transport Layer HTTP/1.1 atau HTTP/2 Biasanya HTTP/1.1 (POST) Wajib HTTP/2 atau HTTP/3
Type Safety Lemah (Perlu OpenAPI / Swagger terpisah) Sangat Kuat (Schema SDL) Sangat Kuat (.proto Code Gen)
CDN Cacheability Sempurna (Native HTTP Cache Headers) Buruk (Semua via POST ke 1 URL) Tidak Dirancang untuk Public CDN
Kecepatan & Latensi Standar Lebih lambat (Parsing AST kueri di server) Paling Kilat (Sub-milidetik)

6. Production War Stories & Anti-Patterns

War Story: DoS Akibat Query Nesting GraphQL Tanpa Batas
Sebuah startup fintech membuka endpoint GraphQL publik mereka tanpa pembatasan kedalaman kueri (Query Depth Limiting).

Seorang penyerang mengirimkan kueri bersarang rekursif:
query { user { friends { friends { friends { friends { friends { id } } } } } } }

Server GraphQL mencoba mengeksekusi kueri pohon dengan jutaan relasi basis data, menghabiskan 100% CPU dan RAM server dalam hitungan detik.

Mitigasi Wajib: Terapkan Max Depth Limiting (maksimal 4 level) dan Query Cost Analysis (menolak kueri yang menghitung lebih dari 1000 titik kompleksitas).
