Modul 21: Orkestrasi Kontainer: Docker Compose Menuju Kubernetes

Evolusi dari satu server menuju kluster terdistribusi: transisi Docker Compose lokal ke arsitektur kluster Kubernetes, dekonstruksi hierarki Pods, Deployments, Services (ClusterIP/NodePort/LoadBalancer), Ingress Routing, Health Probes (Liveness & Readiness), serta strategi rilis Canary tanpa downtime.

1. Mengapa Docker Compose Tidak Cukup di Produksi?

Docker Compose adalah alat luar biasa untuk pengembangan lokal: ia mengorkestrasi multi-kontainer (App, Redis, PostgreSQL) di satu mesin laptop menggunakan DNS bridge network internal.

Namun di level produksi industri berskala jutaan pengguna:

  • Jika server fisik tempat Docker Compose berjalan mati listrik → Seluruh aplikasi mati total!
  • Docker Compose tidak bisa melakukan Auto-Healing lintas mesin fisik server yang berbeda.
  • Docker Compose tidak mendukung Horizontal Pod Autoscaling (HPA) dinamis berdasarkan lonjakan beban CPU/RAM.

Untuk mengatasi ini, Google menyumbangkan Kubernetes (K8s) ke Cloud Native Computing Foundation (CNCF) sebagai standar de facto orkestrasi kontainer dunia.

2. Primitif Inti Kubernetes: Pods, ReplicaSets & Deployments

Unit Terkecil
Pod
Membungkus 1 atau lebih kontainer. Semua kontainer di dalam Pod berbagi IP address yang sama dan dapat berkomunikasi via localhost!
Penjaga Jumlah
ReplicaSet
Memastikan jumlah replika Pod yang berjalan selalu sesuai dengan target deklaratif (misal: selalu 3 Pod aktif).
Pengelola Rilis
Deployment
Mengontrol siklus hidup pembaruan versi (Rolling Update), rollback instan, dan deklarasi image baru.

3. Abstraksi Jaringan: Kubernetes Services & Ingress

Karena Pods di Kubernetes bersifat fana (*ephemeral* — bisa mati dan dibuat ulang dengan IP baru kapan saja), kita tidak boleh mengarahkan trafik langsung ke IP Pod. Kita menggunakan Kubernetes Service:

Tipe Service Cakupan Akses Karakteristik Operasional
ClusterIP (Default) Internal Kluster Saja Memberikan 1 IP Virtual stabil yang membagi beban (*Load Balance*) ke seluruh Pod target via iptables/IPVS.
NodePort Akses Eksternal Tertentu Membuka satu port statis bernomor 30000 - 32767 di setiap server node fisik dalam kluster.
LoadBalancer Publik Internet Penuh Memerintahkan penyedia cloud (AWS ELB, Google Cloud LB) untuk memprovisi Load Balancer publik otomatis.
Ingress Controller Layer 7 HTTP Routing Satu pintu gerbang cerdas (biasanya berbasis Nginx / Envoy) untuk routing berbasis nama domain dan URI path (misal: api.domain.com/v1) serta sertifikat SSL.

4. Penjaga Kesehatan Pod: Liveness vs Readiness Probes

Liveness Probe (Apakah Pod Masih Hidup?)
• Mengecek apakah proses mengalami deadlock atau freeze.
• Tindakan Jika Gagal: Kubernetes akan MEREBOOT / MEMBUNUH Pod tersebut dan membuat Pod baru pengganti!
Readiness Probe (Apakah Pod Siap Terima Trafik?)
• Mengecek apakah aplikasi sudah selesai memuat cache atau menyambung ke database saat awal startup.
• Tindakan Jika Gagal: Pod TIDAK DIBUNUH, namun Kubernetes MENGHENTIKAN pengiriman trafik pengguna ke Pod tersebut sampai ia siap!

5. Strategi Rilis Produksi: Rolling vs Blue-Green vs Canary

  • Rolling Update (Standar K8s): Memperbarui Pod satu per satu secara bergantian (misal 1 Pod dimatikan, 1 Pod baru dinaikkan) hingga seluruh kluster terbarui tanpa downtime.
  • Blue-Green Deployment: Menyediakan 2 lingkungan kluster identik (Lingkungan Biru = Versi Lama, Hijau = Versi Baru). Begitu pengujian selesai, switch trafik dialihkan 100% dalam 1 milidetik di level Router/Service.
  • Canary Release: Mengarahkan hanya 5% trafik pengguna ke Pod versi baru untuk memantau apakah muncul error lonjakan log. Jika aman dalam 1 jam, trafik dinaikkan bertahap menjadi 100%.

6. Production War Stories & Anti-Patterns

War Story: Banjir Error 502 Bad Gateway Saat Deployment Akibat Tanpa Readiness Probe
Sebuah startup fintech melakukan rilis kode baru di Kubernetes menggunakan strategi Rolling Update default.

Setiap kali proses deployment berjalan, ribuan pengguna mengeluh mendapatkan layar putih 502 Bad Gateway selama 10 detik!

Penyebab: Aplikasi Java Spring Boot mereka membutuhkan waktu 12 detik untuk inisialisasi koneksi database saat start. Karena developer tidak mendefinisikan readinessProbe, Kubernetes menganggap Pod baru sudah aktif begitu proses dimulai dan langsung mengalirkan request pengguna ke Pod yang koneksi databasenya belum siap!

Solusi: Pasang endpoint HTTP /health/ready pada spesifikasi deployment Kube. Kubernetes hanya akan mengirimkan trafik ke Pod baru setelah endpoint tersebut mengembalikan status HTTP 200 OK!
