Fase 20: Docker & Containerization Internals

Membongkar apa yang sebenarnya terjadi saat menjalankan docker run: isolasi proses via Linux Namespaces, pembatasan sumber daya perangkat keras via cgroups v2, sistem berkas bertingkat Overlay2 Copy-on-Write, serta pemangkasan ukuran image dari 1.2 GB menjadi 20 MB menggunakan Multi-Stage Distroless.

1. Mitos Terbesar: "Kontainer Adalah Virtual Machine Mini"

Banyak insinyur salah mengira bahwa kontainer Docker memuat kernel sistem operasi mandiri seperti halnya VMware atau VirtualBox:

Virtual Machine (Hypervisor Hardware Emulation)
• Menjalankan Guest OS dan Kernel terpisah di atas Hypervisor (Type-1 / Type-2).
• Sangat berat (overhead RAM gigabyte, boot time hitungan menit).
• Emulasi perangkat keras fisik virtual.
Kontainer Docker (Proses Linux Terisolasi)
• TIDAK MEMILIKI KERNEL SENDIRI! Seluruh kontainer berbagi 1 Host Kernel Linux yang sama.
• Kontainer hanyalah sebuah proses Linux biasa yang dipasangi "kacamata kuda" melalui Namespaces dan dibatasi pemakaian CPU/RAM-nya melalui cgroups.
• Start time instan (kurang dari 100 milidetik)!

2. Linux Namespaces: Fondasi Isolasi Lingkungan

Kernel Linux menyediakan 6 primitif namespace yang membatasi apa yang dapat dilihat oleh sebuah proses:

Linux Namespace Apa yang Diisolasi oleh Kernel? Efek di Dalam Kontainer
PID Namespace Nomor identitas proses (Process ID) Aplikasi di dalam kontainer merasa menjadi PID 1 (init), padahal di host OS nomor PID-nya adalah 38402.
NET Namespace Perangkat jaringan, IP address, port routing Kontainer memiliki IP privat sendiri (eth0) dan routing table terisolasi.
MNT (Mount) Titik mount sistem berkas (Filesystem root) Proses hanya bisa melihat root directory / miliknya sendiri (chroot di atas steroid).
UTS Namespace Hostname dan Domain name Kontainer dapat memiliki hostname unik sendiri tanpa mengubah hostname host OS.
IPC Namespace Inter-Process Communication (Shared Memory) Mencegah proses membaca memori bersama milik proses lain di luar kontainer.

3. Control Groups (cgroups v2): Membatasi Sumber Daya

Jika Namespaces membatasi apa yang bisa dilihat, maka cgroups v2 membatasi berapa banyak sumber daya yang boleh dipakai:

Pembatasan CPU & Memory OOM Killer
Ketika Anda menjalankan: docker run -m 512m --cpus="1.5" ...:

1. Memory Throttling: Jika kontainer mencoba mengalokasikan RAM lebih dari 512MB, kernel Linux akan memicu OOM (Out-of-Memory) Killer dan membunuh proses kontainer dengan sinyal SIGKILL (Exit Code 137).
2. CPU Quota (CFS Scheduler): Kernel membatasi durasi siklus CPU proses tersebut dalam jendela 100ms menggunakan CFS (Completely Fair Scheduler), mencegah satu kontainer nakal memonopoli seluruh core prosesor server!

4. Storage Driver Overlay2 & Copy-on-Write (COW)

Bagaimana 10 kontainer dari image Ubuntu yang sama bisa berjalan serempak tanpa memakan ruang disk 10x lipat? Jawabannya adalah sistem berkas Overlay2:

Layer Bawah
lowerdir (Read-Only)
Lapisan image Docker statis yang di-cache di disk dan dipakai bersama oleh seluruh kontainer.
Layer Atas
upperdir (Read-Write)
Lapisan ephemeral tipis khusus milik kontainer tertentu yang menyimpan modifikasi file.
Tampilan Terpadu
merged view
Kernel menyatukan lowerdir dan upperdir menjadi satu tampilan sistem berkas utuh bagi aplikasi.

Mekanisme Copy-on-Write (COW): Saat kontainer ingin memodifikasi file di lowerdir, kernel menyalin file tersebut ke upperdir terlebih dahulu, sehingga file asli di image tidak pernah terkontaminasi!

5. Best Practice: Multi-Stage Build & Distroless Minimal Image

Jangan pernah mem-push image berukuran 1.2 GB yang masih berisi compiler GCC, Node.js SDK, git, dan shell bash ke production. Gunakan Multi-Stage Build dengan Google Distroless:

Dockerfile Multi-Stage Produksi
# TAHAP 1: Build Environment (Besar: ~900 MB)
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# TAHAP 2: Production Minimal Image (Kecil: ~45 MB!)
# Distroless TIDAK MEMILIKI package manager, shell bash/sh, atau curl (Bebas CVE Exploit!)
FROM gcr.io/distroless/nodejs20-debian12
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
USER nonroot:nonroot
CMD ["dist/index.js"]

6. Production War Stories & Anti-Patterns

War Story: Menjalankan Kontainer Sebagai Root Mengakibatkan Host Server Dikuasai Hacker
Sebuah aplikasi web menjalankan kontainer Docker dengan konfigurasi default (user root di dalam kontainer).

Aplikasi tersebut memiliki celah eksekusi perintah arbitrer (Remote Code Execution - RCE). Hacker berhasil mengeksekusi shell di dalam kontainer. Karena kontainer berjalan sebagai root dan memiliki flag mount yang ceroboh, hacker melakukan Container Escape dan mendapatkan akses root penuh di sistem operasi server utama (Host OS)!

Aturan Wajib Keamanan Kontainer:
1. SELALU definisikan user non-root (USER node atau USER 1001).
2. Gunakan Distroless Image yang tidak memiliki binary sh atau bash, sehingga hacker tidak memiliki shell interaktif untuk mengeksploitasi sistem!
